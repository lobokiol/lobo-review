### 项目一：医院导诊问答智能体  2025.07--至今

**项目背景**  
面向医院小程序/导诊台场景的智能问答系统，采用「JWT 网关鉴权 → 实体提取 → 槽位门禁 → 急诊护栏 → 症状 RAG / 疾病查表 → 科室规则消歧 → 答案生成」分层架构。LLM 本身只会生成文字，外层 **Harness 套具**将其约束为可控导诊流程：症状链通过 ES-BM25 + kNN 混合召回，结合 department_rules 规则打分、LLM 结构化澄清（0~3 轮）与置信度门禁完成科室消歧；疾病链走结构化 KB 直查科室；追问链经 MCP 调用医院工具（值班预约、科室介绍、来院路线）。完整生产版集成 vLLM 私有化与 HIS；GitHub 开源仓聚焦可演示的核心 Agent 链路（FastAPI + LangGraph + ES + DashScope 主备模型 + Redis + SQLite + JWT/微信网关 + MCP Mock + Web/CLI 双端）。

**核心职责**

- **Agent Harness（运行套具）**：`app/graph/builder.py` 设计 17 节点 LangGraph 状态机，将「决策 → 槽位填充 → 急诊门禁 → 检索 → 消歧 → 生成回答」固化为显式流程，LLM 仅在 decision / symptom_clarify / dept_disambiguation / dept_confidence 等指定节点调用；`chat_service.chat_once_async()` 作为统一入口，负责读写 Checkpoint、整体超时兜底、收集 node_trace、异步落库。典型兜底设计：reject / rag_miss_reject / low_confidence_reject（置信度 <60 拒答）；NER LLM 失败回退 catalog 词典扫描；answer_generate 无锁定科室时禁用 LLM、返回固定文案——「不信任模型输出，用规则兜住」。
- **路由与领域建模**：定义 NER/检索/规则打分/LLM 追问等输入输出 Schema；三路由 disease / symptom / reject 驱动疾病链与症状链分流；词典/catalog 兜底 + 俗语归一；AppState 统一管理槽位表、澄清选项、科室候选与置信度。构建 **Agentic 多轮澄清闭环（HITL loop）**：`symptom_clarify` / `dept_disambiguation` 澄清节点经 `end_ask` 边走 `END` 挂起并 Checkpoint 持久化，用户下一轮回复后由 `trim_history` 条件边重新路由回澄清节点续跑（0~3 轮，触顶 fallback，截断200个字）——用 LangGraph **循环边**实现有状态多轮对话，而非线性一次性调用；拒答后保留 messages、清空导诊状态。
- **槽位门禁与医疗护栏**：TriageSlotTable + slot_gate（主症/主病至少一项）；emergency_gate 硬规则优先急诊；dept_confidence 低置信拒答；低 margin 触发 LLM 结构化追问（上限 3 轮），触顶 fallback。
- **RAG 与知识库**：EShybrid 召回（BM25 + kNN + rerank_by_alliance），embedding / hybrid 失败回退纯关键词；疾病 KB 支持本地 JSONL 兜底；维护 rag_knowledge、disease_kb、rag_department_rules 三类索引；索引 mapping、embed 入库与查询 pipeline 联调。
- **MCP 工具集成**：Stdio MCP 客户端对接 hospital_mcp（HIS），支持 get_oncall_appointments / 科室介绍 / 步行路线；mcp_followup 节点识别追问意图并路由工具调用。
- **API Gateway Harness（网关套具）**：`app/gateway/` 实现生产级接入层——JWT Access/Refresh 双 Token（HS256）、手机号 E.164 归一化与 SQLite 用户库、Redis Refresh 轮换与每号上限；`/auth/register|login|refresh|me` Web 登录 + 微信小程序 `code2session`/手机号解密；`slowapi` 按用户/IP 限流（`/chat` 可配置，默认关闭便于评测）；全局异常处理器统一 422/429/500 结构化响应；CORS 支持 Web 与 `servicewechat.com`。
- **Eval Harness（评估套具）**：`scripts/` 形成「跑批 → 打分 → 出报告 → 迭代」**自动迭代闭环**——`run_medical_data_batch.py` 经 `auth_helper.py` 带 JWT 批量调 `/chat` 跑 100 条用例，`run_case` 内 `for step in range(max_steps)` **多步对话循环**配合 `batch_clarify_persona` 自动应答多轮澄清（模拟病人），无需澄清即退出、触顶记 timeout；`build_medical_eval_table.py` / `build_eval_round_report.py` 从 SQLite 拉结果产出 `exports/medical_small_100_eval_table.csv`；`eval_round_common.py` 定义固定指标 A（推荐成功率，目标 ≥80%）、B（科室相关性 ≥70 分占比）、D（总体成功率）；`run_all_eval_rounds.py` 以 `for` 循环自动跑 round 3–7，每轮打分后读 `metric_A`，达标（≥80%）**提前退出**、否则继续迭代。另含 Golden 分层评测（A 召回 / B·F 科室 / C 疾病 / D 拒答 / E 急诊）。
- **Test Harness（测试套具）**：`tests/` 下 25+ 个 pytest 模块覆盖路由、急诊门禁、RAG 召回、MCP、JWT 鉴权、限流、超时兜底、LLM fallback 等，monkeypatch 替换 LLM/MCP 调用；`golden_cases.json` + `batch_100_cases.json` 标注集，配 `run_eval.py` 做 NER/路由回归。
- **可靠性 Harness**：LLM **主备 fallback**（`qwen3.6-flash` → `deepseek-v4-flash`，invoke/ainvoke/structured_output 全链路）；`chat_once_async` **整体超时兜底**（`CHAT_TIMEOUT_SECONDS` 默认 60s，超时 HTTP 200 + `timed_out=true` 固定文案）；Redis Checkpoint **四级回退** Redis → RediSearch 缺失时 SQLite → 均失败 MemorySaver；SQLite triage_recorder 异步写入完整导诊周期；SessionManager 管理 user ↔ thread 元数据；`/ready` 聚合 ES/ Redis / SQLite / LangGraph 四项检查，前端可感知 `degraded` 状态。
- **双端演示与部署**：React + Vite Web 前端（手机号登录、JWT 自动刷新、多轮澄清/科室多选、斜杠命令、RAG 溯源展示、Readiness 状态条），`chatLoop.ts` 将每轮响应循环映射为 awaiting_clarify / awaiting_dept / settled 阶段驱动多轮 UI；Rich CLI 以 `_loop()` REPL 交互循环支持 `--phone/--password/--token` 登录；Docker Compose 一键拉起 API + Redis + ES。
- **可维护迭代**：线上问题通过维护知识库闭环；按 SPEC → PLAN → BUILD → TEST → REVIEW → SHIP（superpower）流程，使用 Cursor 完成功能迭代。

**项目成果**

- **生产评测**（450 条 Golden）：症状和疾病科室≥90%、急诊 100%、误推≤5%。
- **开源仓评测**（Batch 100）：意图路由准确率 97%、NER 准确率 81%、综合通过率 80%
- **交付物**：GitHub 开源仓含 Web 演示页（`front_Web/`）、录屏 GIF、Docker 部署方案；面试可现场演示 CLI / Web 双端多轮导诊全链路。

### 项目二：数据智能场景（SSG）2024.07--2025.07

**项目背景**  
驻场 SSG（Server & Storage Group）数据智能场景，面向业务/分析人员自然语言问数与 DaaS I&C AI Use Case 交付；负责 SSG POC 个人工作站后端接口、AiForce（类似 Dify）Pipeline 编排、问数链路修复及 Spark 批量验证自动化。

**核心职责**

- AiForce Pipeline 与工作流编排：基于 AiForce（类似 Dify）搭建问数 Pipeline，编排「意图理解 → 语义解析 → Spark/SQL 生成 → 结果回传」工作流，支持用户通过 SSG Spark 以自然语言提问并稳定获取数据结果；对接业务问法与指标口径，迭代 Prompt 与节点参数。
- DaaS I&C AI Use Case 问数链路开发：修复 DaaS I&C 场景下用户问数无法命中正确结果的问题；排查语义映射、SQL/Spark 生成与数据源路由；实现指定回答格式（表格/字段约束/结构化 JSON）的输出控制。
- Chrome 插件 · Spark 批量验证 Agent：自研 Chrome 扩展，串联 SSG Spark 批量执行 → 采集结果 → Agent 自动校对（设置校对规则）→ 生成优化建议 → 输出测试报告闭环；将原先需 2~3 小时的人工逐条验证压缩至 30 分钟内产出完整测试报告。
- SSG POC 个人工作站 · 后端接口开发：参与 SSG POC 个人工作站服务端接口设计与实现，为前端问数交互与 AiForce Pipeline 提供 REST/API 层支撑。

**项目成果**

- 问数 Pipeline 在 AiForce 平台稳定上线，覆盖 SSG Spark 核心问数路径。
- DaaS I&C Use Case 问数命中率与指定格式输出达标，支持客户侧演示验收。
- 批量验证插件将单次回归耗时降低约 80%+（2~3h → <30min），形成可复用 Agent 校对 + 报告模板。
- SSG POC 个人工作站后端接口交付完成，支持问数 POC 演示与联调验收。
