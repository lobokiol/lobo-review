## 1. 采购报价 Tool：入参、返回与描述怎么设计？

**问（还原）：** 如果要做一个查询供应商报价的 Agent Tool，数据在飞书多维表格里，你会定义哪些入参？工具描述怎么写？

**现场回答概要：** 回答提到了表名、表头、供应商名称、采购物品信息等参数，也提到在描述里指定“数据处理专家”角色。但没有将工具输入、输出、约束和错误契约结构化。

**评分：4.5 / 10** — 知道要查表和带条件，但未回答 Tool schema 设计的核心。“你是数据专家”是 Prompt 角色设定，不是 Tool 描述。

**这题的正确回答骨架：**

| 层次 | 应说的内容 |
|------|--------------|
| 输入 schema | `item_name`、`specification`、`quantity`、`currency`、`region`、`supplier_name?`、`effective_at?`、`top_k?` |
| 输入校验 | 物料名与规格必填；数量为正数；日期、币种、供应商名称用标准化值 |
| Tool 描述 | 说明“查询什么数据、什么条件下调用、不处理什么情况”，避免模糊动词 |
| 输出 schema | 供应商、含税/未含税单价、币种、报价日期、有效期、匹配度、数据来源链接 |
| 异常契约 | 空结果、多义规格、过期数据、权限不足、飞书 API 失败要分别返回 |

**参考答：**

> 我会先把它定义成只读查价 Tool，不让模型写多维表。必填入参是物料名、规格和数量，可选是供应商、币种、地区和报价日期。描述明确说“只返回匹配报价及来源，不作价格判决”。返回结构带单价、币种、有效期、匹配度和数据链接；空结果、过期和模糊匹配返回不同的 machine-readable 错误码，交给主流程决定是否追问。

## 2. 报价过期：Tool 内部删除还是让 Agent 决策？

**问（还原）：** 如果查出的报价已过期，你会在 Tool 内部处理，还是让 Agent 感知并自己决策？

**现场回答：** 不继续访问，抛出错误、记录，人工更新报价；不让 Tool 自动更新。

**评分：6.5 / 10** — 不让工具情况不明地更新业务数据，方向是对的。但只说了“报错”，没分清过期数据是否仍可读，也没说明由哪一层做决策。

**更好的分层：**

1. Tool 负责事实检查：返回最新报价与 `is_expired` / `expired_at` / `last_valid_quote` 。  
2. 规则层负责业务约束：过期且超过容忍窗口则不能作为正式报价。  
3. Agent 负责对话行为：追问是否接受历史价、发起人工索价，或直接转人。  
4. 写操作必须走显式审批/工单，不由读取 Tool 隐式触发。

## 3. RAG 固定 500 字切片：切片、检索、拼接的问题与优化

**问（还原）：** 内部知识库使用固定 500 字切片，直接召回给模型，且没有 rerank，导致结果经常不相关。请分别说切片、检索、拼接三个环节的问题和优化。

**现场回答概要：** 识别出固定字数会把主题切断，建议使用重叠切片；又说了用标签、性别等元数据缩小检索范围。但对 rerank 、query 处理、上下文拼装的回答不清晰，且将“拼接”误解为图片/多媒体信息拼接。

**评分：4.5 / 10** — 切片和 metadata filter 方向有效，但没有正面回答题目的三段论证。这是本场最重要的失分题。

**参考答（可直接复述）：**

> 我会分三段排查。第一是切片：固定 500 字容易把标题、表格和步骤说明切开，改成按标题/段落的语义切块，设置 10%–20% overlap，并将文档标题、层级、产品版本、生效时间作为 metadata。第二是检索：不只做向量 top-k，而是 query 改写/结构化过滤 + BM25、kNN 混合召回 + reranker，并分别观测 recall@k 和 rerank 后 nDCG。第三是拼接：按 rerank 后的分数、文档来源和 token 预算选择连续切块，去重后组装上下文，而不是简单把 top-k 乱序拼进 Prompt。空召回或低分命中要拒答/追问，不要强行生成。

## 4. 如果只能优化一个 RAG 环节，选哪个？

**现场回答：** 选择先做标签过滤，缩小检索范围。

**评分：6.0 / 10** — 对有强结构化条件的领域有效，尤其是导诊中性别、年龄、症状部位对召回范围的限制。但对通用企业知识库，不能设定一律先做标签；应先看基线指标判断是 recall 不足还是 precision 不足。

**改进说法：**

> 我不会先指定某个技术。先用一小批已标注 query 分析问题：如果 recall@20 低，先修 query 理解、切片和混合召回；如果 recall 高但 top-3 乱，先加 rerank 和 metadata filter；如果检索正确但回答乱，修 context packing 和生成约束。导诊这类场景结构化 filter 收益大，但这是结果，不是不看数据的预设。

## 5. 请讲一个真实多步 Agent：任务如何拆解，步骤怎么依赖？

**现场回答概要：** 以医院导诊讲解：输入症状 → 实体提取填槽位 → 四类意图路由（症状/疾病/急诊/其他）→ 症状链的部位澄清、候选科室症状多选、科室打分；疾病链直推科室；急诊/其他直接结束。

**评分：7.0 / 10** — 这是本场相对好的一题，有真实系统、状态和分支。但应先给“状态机”总结，再举症状链，否则容易陷入细节。

**参考答：**

> 这是一个多步状态机，不是多 Agent 并发。依赖关系是：先抽取槽位，再路由；只有症状路由才会进部位澄清；部位完整才会召回候选科室；科室锁定且置信度通过后才能查 HIS 值班。每步都有前置条件、输出 state 和失败路径，所以可以用单元测试覆盖而不是只看最终答案。

## 6. 工作流中一步失败，怎么处理？

**现场回答：** 跳出流程，返回无法获得科室信息，并将问题记录到数据库，便于后续作为 bad case 维护。

**评分：5.5 / 10** — 有记录和维护意识，但把所有节点失败都处理成立即结束，忽略了可重试、可降级和可跳过的区别。

**参考答：**

> 先按节点和错误类型处理。短暂网络错误、429 或可用的主备模型，可以有上限重试/切备；检索失败可回退到关键词检索；HIS 失败不应否定已锁定的科室，只降级为“暂无法查询挂号”。只有关键前置如槽位不足、无法锁定科室或低置信才走拒答。所有路径写入 node trace 和结构化错误码，再进 badcase 回归。

## 7. Agent 怎么评测？数据从哪里来？

**现场回答概要：** 分三层：

1. 识别/实体提取评测，用人工标注与生成数据验证。  
2. 单元测试，每次功能更新后回归。  
3. 场景级测试，覆盖症状、疾病、急诊、一轮/多轮等用例。

**评分：7.0 / 10** — 分层方向是对的，但指标没有报出来，且“生成数据”与“生产标注数据”的作用未区分清楚。

**应统一的口径：**

> 我们有三类集合：一是开发自测的 Batch100，主要用来跑回归和验证新功能；它包含 AI 生成后人工校对的样本。二是生产侧约 450 条人工标注 Golden，用于看症状/疾病科室准确率和急诊命中。三是单元测试，对状态机、规则、拒答和降级做确定性回归。我不会用一个“总准确率”代替这三层。

## 8. 100 条与 450 条用例怎么构建？线上翻车怎么修？

**现场回答：** 100 条为自研自测，含生成数据；450 条为现场收集、人员标注的数据。翻车后主要补俗名、修正年龄规则、在规则筛选时排除与性别不匹配的症状；也举了“发热”在现场应优先指向发热门诊而不是内科的例子。

**评分：7.5 / 10** — 有真实的 badcase 闭环和可操作的修复点。不足是未说清数据集治理：标注规范、版本、分层抽样和修复后的回归门禁。

**应补的一句话：**

> 每个 badcase 不是只改数据，而是先标注为召回、规则、槽位、澄清、置信度或生成问题，再修知识/规则/代码，把该用例纳入回归集。所有指标按数据集版本记录，防止只看总分而某类用例退化。

## 9. 三轮澄清是拍脑袋还是数据得出？新证据怎么处理？

**现场回答概要：** 从早期“大量问句→科室”和知识图谱方案迁移到槽位/规则方案，原因是前者效果不好且难维护。对用户在澄清过程中提出槽位之外的新证据，回答为不是疾病/症状/急诊就拒答并记录。

**评分：5.0 / 10** — 方案演进讲得出来，但没有正面回答“3 轮为何是 3”，新证据也不应被盲目当作“其他”拒绝。

**参考答：**

> 3 轮是产品体验与评测的硬上限，不是一个神奇数字：前两轮优先补高信息增益槽位，第 3 轮后若仍无法锁定科室则转人/拒答，防止无休止追问。用户新输入先重新跑意图和实体抽取；如果命中急诊或新疾病证据，应重置旧澄清分支并重新路由，不是继续死追上一个问题。

## 10. 反问、岗位信息与匹配度

**候选人反问：** 岗位职责是什么？

**面试官回答（整理）：** 有两类定位：

1. 大模型开发工程师：面向具体需求做大模型/智能体开发与交互。  
2. 智能体专家：为公司建立智能体规则体系与开发方向，支撑业务部门交付。

**匹配判断：**

| 方向 | 匹配度 | 原因 |
|------|----------|------|
| 大模型应用开发 | 中上 | Agent 编排、RAG、工具调用、评测经验可迁移 |
| 智能体规则体系专家 | 中等 | 有门禁、规则、测试体系，但本场展示的 Tool/RAG 方法论不够稳 |
| 底模训练或算法研究 | 低 | 候选人的经验是应用工程，非微调/预训练方向 |

**反问可以更尖锐：**

> 您提到的“规则体系”，当前是否已经有 Tool schema、评测集、质量门禁和发布流程？还是希望新人从 0 到 1 搭建？这会决定我前 90 天更重视业务接入还是平台治理。

## 综合复盘

### 做得好的地方

1. 面对真实导诊项目时，能说清槽位、路由、症状/疾病链和澄清交互。  
2. 有评测、单元测试、线上 badcase 回溯意识，这比只讲 Prompt 的候选人强。  
3. 知道导诊规则应随院方业务口径调整，例如发热可以优先导向发热门诊。  
4. 没有虚构微调、小程序或未做过的经验。

### 本场核心问题

1. **没有先给结论和结构**：面试官问“三个环节”，应先逐一报答案再展开，不应达到第一个点后发散。  
2. **没有用工程契约语言**：谈 Tool 却没有说 input/output schema、校验、错误码、幂等、权限和审计。  
3. **不善于处理假设业务题**：采购报价场景多次往导诊槽位表引，面试官已明确提示“根据命题来”。  
4. **无法用数据调度方案**：比如 RAG 优先改哪个环节、规则兜底占比多少等题，不能只给直觉判断。  
5. **口径风险仍存在**：置信度应统一为 0–100 / 60 分门禁，不要口述成 0–10 / 6 分。

### 下一轮要练的五个能力

1. **Tool design 模板**：每次先说目的、输入、输出、校验、异常、权限/幂等。  
2. **RAG 三段模板**：切片→召回/rerank→context packing，每段都说问题、解法和指标。  
3. **假设题先拆需求**：不足以设计时，明确说假设，列出三个需求问题，再给 MVP 方案。  
4. **失败分类**：重试、切备、降级、拒答、转人各自适用于什么错误。  
5. **说出仓库里的硬证据**：OpenSearch hybrid、Golden 450、Batch100、pytest 模块、MCP 超时降级、以及对应的指标。
