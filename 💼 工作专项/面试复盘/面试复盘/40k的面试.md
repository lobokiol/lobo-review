### 1. 请介绍你的工作经历和最近负责的项目

**建议回答：**

“我早期主要做软件测试、自动化测试和测试开发，这段经历让我对质量、异常场景和系统可恢复性比较敏感。2024 年以后，我的工作重点转向 AI 应用工程。最近重点落地的是一个小说转 AI 短剧的内容生产平台，我承担 AI 应用和后端方向的核心工作，包括需求拆解、架构设计、Agent 编排、RAG、模型 Provider 接入、异步任务、接口开发和测试验收。

### 2. 如何理解 Workflow、Agent 与 Harness 的区别

**建议回答：**

“Workflow、Agent 和 Harness 解决的是三个不同层面的问题。

Workflow 负责确定性的业务顺序，例如小说导入后必须先抽取事件，再做故事骨架、改编策略和剧本。它的优点是可控、可审计，缺点是面对开放问题时灵活性有限。

Agent 负责在目标和约束下动态决定下一步，可以选择工具、补充上下文、生成内容或发起修复。它适合处理自然语言理解和开放式创作，但必须限制最大步数、工具范围和退出条件。

Harness 是包在 Agent 外面的工程运行层，不等于人工审核。它统一管理模型适配、工具绑定、输入输出协议、会话隔离、记忆、流式事件、错误处理和运行时替换。本地项目用 `HarnessAgent` 统一封装 DeepAgents 主 Agent 和 CrewAI 阶段团队。

因此项目不是三选一，而是固定 Workflow 做骨架，Agent 处理需要判断和创作的节点，Harness 保证 Agent 可运行、可观测、可替换。”

### 3. 项目使用了哪些技术栈

**建议回答：**

“前端是 Vue 3、TypeScript、Vite、Element Plus、Vue Router 和 Axios；后端是 Python、FastAPI、SQLModel 和 Alembic。本地可以使用 SQLite，生产建议切换 PostgreSQL。

Agent 层使用 DeepAgents 作为主 Agent 运行时，CrewAI 负责骨架、策略和剧本阶段的多角色顺序协作，外层由自定义 Harness 统一接口。RAG 使用 ChromaDB 和本地 ONNX Embedding，并按项目隔离索引。耗时任务通过 Redis Stream、消费者组和独立 Worker 执行，数据库保存任务事实状态。

模型侧通过统一 Provider Gateway 接入文本、图片和视频模型，避免业务代码绑定某一家厂商。测试以 pytest 为主，覆盖剧本状态、RAG、事件抽取、任务状态和部分接口链路。当前没有把 FFmpeg 最终渲染说成已实现能力。”

AI 可以提高需求分析、编码、测试补全和文档整理效率，但架构取舍、业务边界、生产数据安全和最终验收必须由工程师负责。”

### 5. 你在 Agent / Harness 工程方面做过什么

**建议回答：**

“我在项目里实现了一层独立 Harness，主要做了六件事。

第一，定义统一的 `ScriptAgentInput`、`ScriptAgentEvent` 和 `ScriptAgentResult`，让上层不依赖具体 Agent 框架。第二，封装 `DeepAgentsRuntime` 和 `CrewAIStageRuntime`，主 Agent 与阶段团队可以使用同一套调用协议。第三，通过 `ModelGatewayAdapter`、`ProviderGatewayChatModel` 和 `ProviderGatewayCrewLLM` 把不同 Agent 框架接到统一模型网关。第四，通过 `isolation_key` 和 `thread_id` 隔离用户、项目和对话。第五，绑定项目配置、工作区和章节事件查询工具，并通过 Profile 限制工具范围。第六，把工具开始、成员进度、内容增量和错误统一转成流式事件返回前端。

测试上，我会分别验证运行时适配、工具参数、会话隔离、模型失败、流式事件顺序、阶段回退和端到端业务链路。Harness 的价值不是让 Agent 更聪明，而是让它可控、可替换和可排查。”

### 6. 请讲讲 Agent Loop 的完整设计

**建议回答：**

“这个项目的 Agent Loop 可以拆成七步。

第一，加载项目、用户、会话状态和当前创作阶段。第二，准备项目级 RAG 上下文。第三，DeepAgents 主 Agent读取用户目标，必要时调用项目配置、工作区或章节事件工具。第四，业务层根据结果判断是在回答问题，还是进入故事骨架、改编策略或剧本生成阶段。第五，进入生成阶段后启动 CrewAI 团队，角色按分析、设计、写作和审核的顺序协作。第六，对阶段结果做结构校验和质量评估；不通过时把具体失败原因作为修复上下文重新生成，而不是重复相同 Prompt。第七，保存结果和状态并返回事件流。

退出条件必须明确：任务完成、达到质量标准、超过最大修复次数、模型或工具出现不可恢复错误，或者需要人工确认。每轮都记录阶段、耗时、工具调用、错误和结果，避免无限循环。”

### 7. Agent 如何自循环、重写和控制质量

**建议回答：**

“我采用的是受限修复循环，不让 Agent 无限制自我反思。

质量控制分三层。第一层是确定性校验，例如结构是否完整、分集数量是否符合配置、剧本块格式是否正确、必填字段是否缺失。第二层是内容评估，例如原著事实一致性、人物一致性、情节完整性、节奏和可拍摄性。第三层是人工确认，适用于低置信度、连续修复失败或业务方需要把关的内容。

校验失败后系统生成带缺陷列表的 repair message，只修复失败部分。修复次数由常量限制，超过上限就停止，并保留原输出、失败原因和历史尝试。这样既控制 Token 和延迟，也避免模型在多轮重写中偏离原著。”

### 8. Human-in-the-loop 如何设计

**建议回答：**

“HITL 不应该只是页面上放一个确认按钮，而应该是可恢复的状态迁移。

在这个项目里，适合设置人工审核的节点包括项目配置确认、故事骨架确认、改编策略确认、分集剧本确认、资产与分镜确认，以及最终剪辑确认。进入人工节点时，需要持久化当前项目、会话、阶段结果、评分、失败原因和下一节点。人工可以通过业务接口确认、修改或退回，系统再从指定节点继续，而不是从头重跑。

当前代码已经具备阶段状态保存、人工修改内容和继续生成的基础，但还没有完整的人工任务中心、领取机制、审批 SLA 和全链路审计。因此面试时我会说‘具备 HITL 基础和审核点’，不会说已经完成企业级 HITL 平台。”

### 9. 人工介入阈值如何确定

**建议回答：**

“阈值不能直接拍一个 0.6，而要通过标注集校准。

短剧场景可以准备一批由编剧或业务方审核过的骨架、策略、剧本和分镜样本，记录是否可直接通过、需要修复还是必须人工重做。然后比较不同阈值下的自动通过准确率、错误放行率、人工介入率、平均修复次数、Token 成本和延迟。

上线初期我会优先控制错误放行，阈值偏保守；积累真实审核数据后再逐步降低人工比例。高风险维度不能只看平均分，例如角色关系严重错误或关键剧情与原著冲突，即使总分较高也应该直接进入人工审核。”

### 10. AI 结果与人工标准答案如何匹配和评分

**建议回答：**

“剧本生成没有唯一标准答案，所以不能只用整体语义相似度。我的评测会分成确定性指标和主观指标。

确定性指标包括输出 Schema 合法率、必填字段完整率、人物和地点引用正确率、分集数量、镜头数量以及工具调用成功率。内容指标包括原著事实一致性、人物一致性、情节覆盖、节奏、台词质量和可拍摄性。内容指标可以使用 LLM Judge 做初评，但要用人工标注集校准，并定期检查模型评分与人工评分的相关性。

最终保留模型分、人工分、是否通过、修改原因和修改后的版本。评测重点不是让生成结果逐字接近参考答案，而是验证它是否满足业务约束并保持原著核心事实。”

### 11. 状态迁移如何设计，人工能否修改状态

**建议回答：**

“状态需要分成业务状态和运行状态。业务状态包括当前处于故事骨架、改编策略、剧本、资产、分镜还是视频阶段；运行状态包括 pending、queued、running、succeeded、failed、cancelled 等。

剧本对话按项目、用户和 conversation 生成 `isolation_key`，状态持久化到数据库；同一会话使用锁避免并发写入。图片和视频等长任务由数据库保存事实状态，Redis Stream 只负责调度，Worker 完成后 ACK；失联任务可以从 PEL 认领并恢复。

人工可以修改业务内容和执行审核动作，但不能直接随意修改数据库任务状态。状态变更必须通过服务接口，校验当前状态是否允许迁移，并记录修改前后内容。这样可以避免任务已经失败却被人工直接改成成功的审计问题。”

### 12. 前置模型产出是单次调用还是循环调用

**建议回答：**

“两种都有，但依据任务风险和不确定性选择。

项目配置读取、状态判断、Schema 校验和任务状态迁移主要由确定性代码完成，不需要循环调用模型。普通问答或意图识别通常一次调用即可。主 Agent 在需要查询项目配置、工作区或章节事件时会进入受限的工具调用循环。故事骨架、改编策略和剧本生成则是多角色顺序调用，质量不通过时才进入有限修复循环。

原则是能用规则解决的不用 Agent，能单次调用解决的不启用循环，只有确实需要补充信息、工具调用或质量修复时才增加轮次。”

### 13. 请具体说明业务交互流程

**如果面试官要求讲当前短剧项目，建议回答：**

“用户先创建项目并配置题材、受众、视觉风格和文本、图片、视频模型，然后导入小说。系统解析章节并提取人物、地点、时间、冲突和情节事件。进入剧本工作区后，主 Agent 读取项目配置和相关章节事件，先生成故事骨架，人工确认后生成改编策略，再生成分集剧本。

剧本确认后，系统抽取人物和场景资产，生成资产提示词和图片；随后生成分镜文本、宫格分镜图和单镜头图，再根据首帧、尾帧或参考图调用视频模型生成单镜头视频。所有长任务进入 Redis Stream，由 Worker 异步执行，前端查看进度并处理失败重试。当前最后一步是保存剪辑时间线工程，TTS、字幕和 FFmpeg 自动成片还未完成。”

**如果面试官仍然指定医疗导诊项目，不能改讲短剧项目，建议回答：**

“用户输入‘肚子疼’后，系统先识别为腹痛相关意图，再追问位置、持续时间、严重程度和伴随症状；把口语归一为标准症状后，结合年龄、风险规则和知识库召回候选科室。系统只做科室推荐和紧急风险提示，不直接给诊断。低置信度时继续追问，高风险时建议立即就医或转人工。”

### 14. 系统是否保留用户历史记忆

**建议回答：**

“本地短剧项目同时使用三类上下文，但用途不同。

第一类是当前会话消息和阶段状态，用于保持本轮创作连续性。第二类是 DeepAgents 的项目/会话隔离记忆，通过 `isolation_key` 映射到独立记忆来源，避免不同项目串线。第三类是项目级 RAG，把小说章节、结构化事件、项目配置和阶段结果写入 ChromaDB，在长篇小说改编时按需召回。

短期状态、长期记忆和业务事实不能混在一起。小说原文、剧本版本和任务状态以数据库为准；向量库只用于检索，不作为最终事实源。医疗项目若被追问，则应强调会话级短期记忆、过期清理、用户隔离和隐私保护，不能照搬短剧项目的长期创作记忆。”

### 15. RAG 的数据来源、构建和召回如何设计

**建议回答：**

“这个项目的 RAG 不是搜索通用影视知识，而是解决长篇小说超过上下文窗口、跨章节事实容易丢失的问题。

数据来源包括项目配置、小说元数据、章节正文、结构化章节事件、人物与场景信息，以及已经确认的骨架、策略和剧本结果。索引构建时按文档类型切分，生成本地 ONNX Embedding 后写入 ChromaDB，并按项目隔离 collection 或 scope。

查询时先识别当前意图和阶段，再结合关键词与向量相似度进行混合召回，同时使用章节范围和文档类型过滤。召回结果只作为上下文交给 Agent，不能覆盖数据库中的项目事实。评测指标包括 Recall@K、人工相关率、原著事实命中率、跨项目串数据率和最终剧本事实错误率。”

### 16. 知识库中的数据包含哪些内容

**建议回答：**

“短剧项目不是单纯的一张 FAQ 表，而是多类文档和结构化实体。

项目配置包括题材、受众、集数、单集时长和视觉风格；小说数据包括小说、章节、标题、顺序和正文；事件数据包括事件 ID、章节范围、人物、地点、时间、冲突和事件摘要；创作数据包括故事骨架、改编策略、分集剧本及版本；制作数据包括人物资产、场景资产、分镜、提示词、图片和视频引用。

向量库保存可检索文本、Embedding、文档类型、项目 ID、章节范围和来源 ID。数据库保存完整业务事实和状态，向量库保存检索副本，两者通过稳定 ID 关联。”

### 17. 相似度匹配算法如何实现

**建议回答：**

“项目采用混合检索，而不是只依赖余弦相似度。

先对查询做归一化和意图识别，再使用本地 Embedding 生成查询向量，从 ChromaDB 获取候选文档；同时计算关键词或词法匹配分。排序时综合向量相似度、词法得分、文档类型、章节距离和当前创作阶段。比如生成第 8 集剧本时，邻近章节事件和已确认的改编策略应该比远距离章节拥有更高优先级。

权重通过标注查询集离线评估，关注 Recall@K、MRR、人工相关率和事实命中率。低置信度时扩大章节范围、改写查询或要求人工确认，不能把低相关文档强行塞进上下文。”

### 18. 这个项目更像 Workflow 还是 Agent

**建议回答：**

“整体是 Workflow 主导、Agent 增强、Harness 托底。

小说导入、事件提取、骨架、策略、剧本、资产、分镜和视频之间有明确依赖，所以主干必须是 Workflow。DeepAgents 主 Agent 负责理解用户目标和选择工具，CrewAI 多角色团队负责阶段内创作和审核，这是 Agent 部分。Harness 统一模型、工具、记忆、事件和错误处理，Redis Stream 负责长任务调度。

我没有选择完全自主的 Agent 群，因为内容生产既需要创造性，也需要成本可控、过程可回溯和人工可修改。固定主流程加局部 Agent，比让多个 Agent 无限制自由协商更适合当前业务。”

### 19. 如何理解这个岗位，你与岗位有什么匹配点

**建议回答：**

“我理解这个岗位不是单纯写 Prompt，而是把文字、图片、音频和视频模型组织成稳定的内容生产系统。核心工作包括业务流程拆解、模型和 Provider 接入、Agent/Harness、长任务调度、人工审核、成本控制、质量评测、日志监控和 SOP 沉淀。

当前小说转短剧项目和岗位的匹配点比较直接：已经覆盖长文本理解、RAG、剧本多 Agent 创作、资产和分镜生成、单镜头视频、异步 Worker 与人工审核点。我能承担 AI 应用后端、Agent 编排和工程化落地，并能利用测试开发背景补齐异常场景、评测和验收。

项目当前的缺口也很明确：可用 TTS、字幕、FFmpeg 最终渲染、完整 HITL 任务中心和生产级可观测性。这些不是我要回避的问题，而是可以按优先级继续建设的工程路线。”

## 适合现场复述的项目定位

> 我负责的是一个小说转 AI 短剧内容生产平台。系统以阶段化 Workflow 为主干，使用 DeepAgents 主 Agent理解任务和调用工具，使用 CrewAI 专业角色团队顺序完成故事骨架、改编策略和分集剧本，并通过 Harness 统一模型网关、工具、记忆、会话隔离和流式事件。长篇小说通过项目级 RAG 召回章节和结构化事件，图片、视频等耗时任务通过 Redis Stream 和独立 Worker 执行。当前已经走通小说到单镜头视频，剪辑工程可以保存时间线；TTS、字幕和 FFmpeg 最终成片仍属于下一阶段。
