## 1. 第一个方案为何失败？现在方案凭什么能维护？

**问（还原）：** 导诊 Agent 你调研时第一个方案怎么做的？为什么推不下去？现在方案解决了什么？

**答（整理）：**

1. **方案 A（翻车）**：大量「用户问句 → 标科室」案例 + 知识图谱推理链：多症状 → 多疾病 → 科室。看起来完整，实际三条致命伤：  
   - **产品边界**：导诊台不能「看病」；图谱路径本质在做诊断，越权且难验收。  
   - **标注成本**：问句→科室标注量巨大、效果差，比标科室还要标一堆中间分类。  
   - **不可维护**：权威医学 KG「客观、不可改」，自己没法迭代。自测都过不了，方案崩掉。  
2. **方案 B（现行）**：知识与规则完全落在自己可控的库里（症状归一、科室规则、疾病 KB），可按现场政治/业务需要改科室映射，能自测、能迭代、能上线。

**评分：8.5 / 10** — 本场最佳题之一：有真实失败、有产品边界意识、有「可维护性 > 看起来高级」的工程判断。

| 维度 | 简评 |
|------|------|
| 技术准确度 | 与仓库演进一致：弃「诊断式图谱」，改 RAG + `department_rules` + 疾病 KB |
| 岗位迁移力 | 运维侧同样忌讳「黑盒大图谱不可改」；应主动映射到「告警规则/拓扑可配置」 |
| 表达清晰度 | 故事完整；「政治出现什么样的科室」等口语可收成「按院方科室目录维护」 |

**参考答案（对齐本仓）：**

> 第一版按 GitHub 常见「问句标注 + 疾病图谱推科室」做，三处过不了关：导诊不能诊断；标注不可持续；权威图谱我改不了。现行方案把可控性拿回来：`rag_knowledge` 做俗语归一，`rag_department_rules` 打分消歧，`disease_kb` 直查科室，LangGraph 显式状态机 + 低置信拒答。上线后坏例改知识/规则，而不是改不可控的外部字典。运维场景同理——故障树/拓扑/告警规则必须在你们平台可配置，而不是绑死外部百科。

## 2. 状态机「死锁 / 脏状态」怎么处理？（记忆迁移）

**问（还原）：** LangGraph 状态机有哪些坑？记忆迁移算不算问题？

**答（整理）：** Checkpoint/记忆可跨轮保留是优点，但导诊里「上一通肚子疼→内科」的槽位不能污染「下一通脚疼」。每次得到科室后要清掉 App 内导诊状态，同时把完整记录写入数据库留痕。

**评分：8.0 / 10** — 命中生产真实坑；与 `triage_state_reset_patch()`「清 triage、留 messages」一致。可补：拒答/低置信/新意图入口也会 reset。

**参考答案：**

> LangGraph Checkpoint 适合多轮澄清续跑，不适合跨主诉复用槽位。我们在得到科室、拒答、或新一轮决策入口调用 `triage_state_reset_patch()`：清空 `slot_table` / `dept_state` / `locked_department` 等，保留 `messages`；完整周期异步写入 `triage_recorder`（SQLite）。运维 Agent 同理：一次故障会话结束后清「当前告警簇 / 假设栈」，审计日志另存。

## 3. 工具调用（HIS/MCP）超时与脏返回怎么兜底？

**问（还原）：** 调外部 HIS/工具系统时，空返回、挂掉、字段不对怎么办？

**答（整理）：** 外部不可控。限制约 **2 秒**；超时或拿不到硬字段（如 Department）则停工具调用，向主流程回「无法获得预约信息」之类固定文案，不把脏结构继续往下传。

**评分：7.0 / 10**

| 维度 | 简评 |
|------|------|
| 技术准确度 | 方向对（超时 + 降级文案）；仓库默认 `MCP_TIMEOUT_SECONDS=5`、整体 `CHAT_TIMEOUT_SECONDS=60`，口播「2 秒」宜统一口径 |
| 岗位迁移力 | 运维调 Prometheus/CMDB/工单 API 同构，应主动讲 schema 校验 |
| 表达清晰度 | 「强硬值 / Department 关键字」听感乱，应用「必填字段校验失败」 |

**参考答案：**

> MCP/`fetch_oncall`：`asyncio.wait_for(..., MCP_TIMEOUT_SECONDS)`（配置默认 5s）；空列表或异常 → `oncall_fetch_error="暂无法获取预约信息"`，主图继续 `answer_generate`，不阻断科室结论。另有整聊超时兜底（默认 60s → HTTP 200 + 固定文案）。运维平台：每个 Tool 定义 JSON Schema + 超时 + 熔断，失败走「人工工单深链」而不是幻觉补全。

## 4. 评测体系怎么分层？

**问（还原）：** 你们怎么评？就靠大模型感觉吗？

**答（整理）——四层：**

1. **槽位/识别评测**：槽位抽取准确率；模型从 2.5-7B 升到 Qwen3-8B 后明显改善。  
2. **需求驱动的单元测试 + CI**：用 Superpowers 走「需求 → 分析 → 规划 → 执行」；每个需求落地带单测；CI 管道每次全量跑历史用例（约几十个）。举例：FAQ/个人记忆别家可能存一周，导诊场景只能 **一天**，否则昨天肚子疼会错误短路今天的推理。  
3. **Batch100**：自研场景集，模型辅助生成；覆盖急诊、疾病链（一轮/两轮）、症状链、拒答、科室消歧等，批量跑端到端。  
4. **Golden ~450**：现场标准人员定标「问句 → 科室」，分类回归。

另澄清：单元测试来源 = AI 生成问句/目标科室 + 开发过程中需求完成沉淀的用例。

**评分：8.0 / 10** — 分层清晰，有「场景约束写进测试」的好例子（FAQ TTL）；指标分子分母仍偏虚。

**参考答案：**

> 四层对齐仓库：  
> 1. NER/槽位：`tests/` + `run_eval.py`。  
> 2. 节点/门禁单测：急诊、`slot_gate`、JWT、限流、超时、fallback 等 25+ pytest，CI 全绿。  
> 3. Batch100：`run_medical_data_batch.py` 多步对话 + persona 自动答澄清；`eval_round_common` 盯 metric A≥80%。  
> 4. 生产 Golden ~450：科室≥90%、急诊 100%。  
> 需求级约束进测试：会话/FAQ 类记忆 TTL 按产品定（导诊偏短），防止「记忆捷径」绕开状态机。

**问（还原）：** 你那套插件/流程是不是要改很多才能适配当前项目？会不会往业务里塞太多东西？

**答（整理）：** 不用大改，直接用；固定从 brainstorming 等步骤起。**不要**把技能/脚手架硬塞进业务仓——业务越简单越好；项目已经够复杂，一个月后可能就结束，没必要堆死代码。导诊是「单轮用户问题 → 目标科室 → 图结束再重启」，token 量可控。

**评分：8.5 / 10** — 面试官明显在测「会不会 AI 屎山」；回答克制、Yagni，加分。

**参考答案：**

> 流程在开发机侧跑（SPEC→PLAN→BUILD→TEST），产物是 PR 与测试，不把 Agent 框架依赖打进运行时。运行时只保留 LangGraph 节点与配置。运维平台 DEMO 已通、年底要上线时，更要防「为用 ADK 而 ADK」——先交付定位/汇聚/工单三条主路径的可评测闭环。

## 6. Token / 上下文会不会爆？

**问（还原）：** 多轮会不会上下文很大、成本很高？

**答（整理）：** 单次导诊闭环短，算过大约一两百～三百 token 量级，主要贵在症状链相似词与部位澄清；不需要按长会话产品那套记忆。

**评分：6.5 / 10** — 方向对，但「两三百」未标明单位（prompt tokens / 人民币 / 单次调用），易被追问穿帮。

**参考答案：**

> 单次闭环：trim 历史 + 结构化槽位，避免全文堆积。成本热点在 `symptom_clarify` / 消歧的结构化调用，可用选项卡减自由生成。报数时说清：「单次 /chat 平均输入输出 tokens ≈ X，Batch100 总成本 ≈ Y」。运维排障会话更长，必须上「告警摘要窗口 + 工具结果裁剪 + 假设栈」，不能照搬导诊短会话假设。

## 7. 症状链：俗语归一 → 部位 → 检索 → 科室？

**问（还原）：** 症状链路具体怎么走？检索用什么？

**答（整理）：** 肚子疼等俗语先归一到「腹痛」等标准词，再追问部位（上/下腹等），再对标准症状做检索召回，关联症状/科室规则打分；用过 **ES**（口语），没用过其他向量库产品。

**评分：7.5 / 10** — 业务链路对；应说 **OpenSearch BM25+kNN hybrid**，避免被「只会 ES 关键词」看扁。

**参考答案：**

> `rag_symptom_recall`（OpenSearch hybrid：BM25 + kNN，失败回退纯关键词）→ `symptom_clarify`（≤3 轮选项）→ `dept_rules_disambiguation` / 低 margin 时 LLM 消歧 → `dept_confidence`（低分拒答）。运维类比：告警文案归一（同义错误码）→ 限定资源对象（集群/域名）→ 检索相似历史事件 → 置信门禁再给处置建议。

## 8. 换语言 / 不用 Python 行不行？Code Review 怎么做？

**问（还原）：** 若技术栈不是 Python，要学别的语言怕不怕？AI 写的代码你怎么保证质量？

**答（整理）：**

- 语言不挑；现在项目基本不手写太多，靠 Review。  
- Review 要点：有单测；自己能看懂、能讲给同事听；讲不清就改。早年 AI 弱时还手改，现在生成太强，要改反而改不动——所以更依赖「能讲清楚 + 测试」。  
- 对 Google ADK：没深用过，但认为语言/框架表层差异大、Agent 原理（工具、状态、评测）差不多，生态好坏是差量。

**评分：7.0 / 10** — 「原理迁移」对岗位加分；「AI 强到改不动」需改成「用测试与小步 diff 管住」，否则像放弃掌控。

**参考答案：**

> 我可以短期切到 Google ADK/你们内部栈：迁移的是状态机、工具 schema、超时降级、Golden 回归，不是 Python 语法。AI 编码的质量门禁是：可讲解的 diff + 单测/评测红线 + 人工 Review；生成物看不懂就不合入。DEMO 已通、要优化交付时，我优先补评测集与工具失败路径，而不是先换花样框架。

## 综合评价

### 优势

1. **架构演进故事强**：图谱方案翻车 → 可控知识 + 状态机，体现产品边界与可维护性，适合「DEMO 要优化成上线」的团队。  
2. **生产脏路径意识**：记忆污染、工具超时、固定降级文案——运维 Agent 同样刚需。  
3. **评测分层完整**：单测/CI + Batch + Golden，契合「年底交付不能靠感觉」。  
4. **Yagni**：明确不把 AI 脚手架塞进业务仓，面试官关心点答到了。  
5. **框架迁移态度正确**：不绑死 Python，谈 Agent 共性。

### 短板

1. **岗位映射几乎缺席**：听完 DNS/告警/工单后没有结构化迁移话术——在「要即战力」的口径下很伤。  
2. **数字口径不稳**：MCP「2 秒」vs 仓库 5 秒；token「两三百」单位不清。  
3. **检索表述偏旧**：口播「ES」未讲 OpenSearch hybrid / 回退策略。  
4. **录音/表达**：专有词含混、中段单向输出多，现场二面需更短分点。  
5. **未反问关键题**：现有 DEMO 架构、数据能否打标、年底范围（MVP 含不含工单）等均未问。

### 与岗位匹配度

| 维度 | 医疗导诊（本仓） | 北森运维 AI 岗 |
|------|------------------|----------------|
| 问题形态 | 相对明确终点（科室） | 开放假设（DNS/链路多因） |
| 状态机 / 工具超时 / 降级 | 现成 | **直接可迁** |
| 评测闭环 | Golden + Batch + CI | **直接可迁**（需换领域集） |
| 告警汇聚 / 拓扑推理 | 弱（多信号仅急诊硬规则等） | **需补** 关联规则与事件模型 |
| Google ADK | 未用 | **短期可学**，勿夸已会 |
| 交付压力 | 有过上线迭代经验 | 年底客户版——需表态砍范围能力 |

**匹配结论：** Agent **工程底座匹配中上**；**运维领域与开放域定位**需二面补齐映射。招聘若真按「来了就能推 DNS 定位上线」考核，本场岗位回应不足以让人安心。

## 能否通过 / 二面怎么打

| 评判项 | 结论 |
|--------|------|
| 技术（编排/评测/降级） | **通过线偏上**（~7.4） |
| 岗位即战力感知 | **偏弱**（题 10 = 5.5） |
| 表达与口径 | **临界** |
| 综合 | **弱通过 → 看现场二面** |

**判断：有机会进现场二面，但非稳过。** 结束语无强录用信号；「经验换时间」说明二面会更盯你能不能把 DEMO 推到可交付。

### 二面优先补三件事

1. **90 秒迁移话术**（上文参考答案）：定位 / 汇聚 / 工单 ↔ 本仓节点与评测。  
2. **口径表**：MCP 5s、整聊 60s、Golden 450、Batch100 metric A、OpenSearch hybrid——背分子分母与脚本名。  
3. **带演示**：本仓 Web 多轮澄清 + 故意断 MCP 看降级；再口述「若换成 Google ADK，节点如何一一对应」。

## 结合本地项目的复盘建议（可执行）

下列建议直接服务「北森运维 AI」叙事，并反哺本仓简历可信度。

### A. 把导诊能力翻译成运维词汇（话术层）

| 本仓能力 | 二面怎么说 |
|----------|------------|
| `emergency_gate` 硬规则 | 致命告警/P0 指纹先规则拦截，不进慢路径 |
| `slot_gate` | 工单必填：集群、域名、时间窗不齐就追问 |
| `rag_symptom_recall` hybrid | 历史故障单 / runbook 混合检索 |
| `symptom_clarify` 选项卡 | 排障决策树选项，降低自由文本漂移 |
| `dept_confidence` 拒答 | 证据不足只给排查清单 + 转人工 |
| MCP 超时 + 固定文案 | 监控/CMDB/工单 API 同样超时降级 |
| `triage_state_reset_patch` | 事件关闭后清假设栈，审计另存 |
| Golden + Batch100 | 用历史 DNS 故障单 / 告警簇建回归集 |

### B. 本仓可立刻核对、避免二面穿帮的点

1. **统一超时口径**：口播与 `MCP_TIMEOUT_SECONDS`（5）、`CHAT_TIMEOUT_SECONDS`（60）一致；若生产真是 2s，改配置再讲。  
2. **检索名称**：对外统一「OpenSearch 混合检索（BM25+kNN）」，「ES」仅作习惯叫法并立刻纠正。  
3. **状态重置触发点**：能指出 `decision` / `reject` / `rag_miss_reject` 等调用 `triage_state_reset_patch`，证明不是「我感觉清一下」。  
4. **评测数字**：Batch100 综合 ~80%、路由 ~97%、生产 Golden 科室 ≥90%、急诊 100%——各绑一个脚本/报告入口。

### C. 若要为北森准备「最小可演示迁移」

不必新造大系统，做 **一页设计 + 可选 stub**：

1. 一张图：`告警接入 → 归一/指纹 → 假设栈状态机 → 工具（DNS查询/日志）→ 事件汇聚 → 工单草稿`。  
2. 说明哪些节点复用本仓模式（门禁、超时、拒答、落库），哪些是新域（关联规则）。  
3. 声明技术栈可换 Google ADK：强调「图与工具契约」，不纠缠语言。

### D. 简历 / 口播微调（针对本岗）

- 个人优势补一句：**「擅长把开放问题收成可评测状态机，并在工具失败时降级」**。  
- 避免只报医疗准确率；加：**「评测驱动迭代（Batch 不达标继续 round）」**——对应他们 DEMO→上线的痛。  
- 诚实写未用过 Google ADK，但列可迁移清单（状态、工具、评测、网关鉴权）。

### E. 表达训练（针对本场转写暴露的问题）

- 每个技术点：**结论 → 机制 → 失败怎么表现 → 对应文件/配置** 四拍，各不超过两句。  
- 听完对方业务后，强制用「所以映射到我们三条能力是…」收尾，杜绝「我没啥问题」式空过。
