## 1. 请简单介绍一下自己

**问（还原）：** 简单说一下你自己和目前做的项目。

**答（现场整理）：**

> 我叫刘博，2014 年毕业。刚毕业时做电气设计，后来转软件测试，2024 年开始从事 AI Agent 设计开发，目前在中软国际做 Agent 开发。我主导了一个医院导诊项目：患者在微信小程序输入症状，Agent 提取关键信息写入槽位表，再根据疾病或症状进入不同链路。症状链包含症状提取、部位消歧和科室消歧，最终推荐科室。我负责从 0 到 1 的开发、验证、私有化部署和协作交付。

**评分：6.5 / 10**

| 维度 | 简评 |
|------|------|
| 技术准确度 | 基本链路对，但「疾病链 / 症状链」和模型边界未讲清 |
| 项目可信度 | 讲了 0→1 和交付，但缺少具体技术栈、节点或评测数字作支撑 |
| 表达清晰度 | 专有词粘连，句子过长；「我主导」后没立即给出可验证产出 |

**更好的 60 秒参考答法：**

> 我叫刘博，12 年软件工程经验，前期做电气和软件测试，2024 年起转 AI Agent 应用开发。我现在主要做医院导诊 Agent：用 Python + FastAPI + LangGraph 组织导诊状态机，症状走 OpenSearch 混合 RAG，疾病走结构化知识库，用规则和置信度门禁决定是否推荐科室。我负责状态机、RAG、评测回归和私有化交付。生产 Golden 约 450 条，科室准确率达到 90% 以上。我的定位是 LLM 应用落地和 Agent 工程化，不是训练底模。

## 2. 项目有没有用大语言模型？部署多大？

**问（还原）：** 你这个项目有没有用大模型？部署的是多少 B？

**答（整理）：** 有使用，本地私有化部署 **Qwen2.5-7B**；`2.5` 是版本，`7B` 是参数量，不是 70B。对当前导诊任务，7B 基本够用。

**评分：6.0 / 10** — 最终口径正确，但「2.57B」被面试官连续追问，现场产生了明显歧义。

**风险点：**

1. 模型名和参数必须停顿说：「Qwen 2.5，7B 参数」。  
2. 「7B 够用」需要证据：任务受限、结构化输出、规则锁科室、Golden 指标达标。  
3. 未讲清私有化推理引擎、GPU 和主备，容易被视为只知模型名。

**参考答法：**

> 生产是 Qwen2.5-7B-Instruct 私有化部署，vLLM 提供 OpenAI 兼容接口，两个实例做主备。这里是「2.5 版本」+「7B 参数」。模型只做意图/实体、澄清和置信度等受限任务，科室结论受规则和门禁约束，所以 7B 在我们的 Golden 集上达标，没有为了参数量盲目换大模型。

## 3. 有没有训练或微调模型？

**问（还原）：** 这个 7B 模型你们有没有做训练？

**答（现场）：** 没有训练，我们有 RAG 就够了。

**评分：5.5 / 10** — 结论可以，但「有 RAG 就够了」过于绝对，把 RAG 和微调说成了可直接互换的手段。

**技术上应区分：**

| 问题 | 优先手段 |
|------|----------|
| 医院知识频繁更新、需溯源 | RAG / 结构化 KB |
| 科室锁定必须可控 | 规则、状态机、置信度门禁 |
| 结构化输出格式不稳 | Prompt/Schema/约束解码，再评估 SFT |
| 领域语言理解长期不达标 | 有标注集后再考虑 SFT/LoRA |

**参考答法：**

> 没做微调，这是基于评测的取舍，不是说 RAG 能代替微调。我们当时的主要问题是知识可更新、科室可追溯与低置信拒答，用 RAG + 结构化 KB + 规则更适合。如果后续在固定结构化任务上长期不达标，我会先构建标注集，再对比 LoRA 微调和现有方案。

## 4. RAG 知识库是你做的吗？

**问（还原）：** RAG 就是本地知识库吗？知识库也是你负责吗？

**答（现场）：** 对，知识库也是我做的。

**评分：5.0 / 10** — 只确认了归属，没有借机证明自己真正做过 RAG。

**应主动补充的最小闭环：**

1. 数据来源和三类索引：症状知识、科室规则、疾病 KB。  
2. OpenSearch 的 BM25 + kNN 混合检索。  
3. Embedding 或 hybrid 失败时回退纯关键词。  
4. 通过 Golden / badcase 调整知识和规则，不是只「建了一个库」。

**参考答法：**

> 是我负责。但严格说不是一个「本地文档库」，而是三类数据：症状俗语和标准词用 OpenSearch 混合检索，科室规则用于打分消歧，疾病 KB 做结构化直查。我负责 mapping、embedding 入库、查询 pipeline 和 badcase 迭代；hybrid 失败时会回退到关键词检索。

## 7. 你的技术栈是什么？

**问（还原）：** 你以前的技术栈有哪些？

**答（现场整理）：** LangGraph、Python，以及智能体开发和 AI 应用落地，主要做后台逻辑。

**评分：5.5 / 10** — 只说了语言和编排框架，技术栈不完整，也没按层次组织。

**建议按层回答：**

> 语言和 API 层是 Python + FastAPI；Agent 编排用 LangGraph；检索用 OpenSearch，包括 BM25 和 kNN；会话和 Checkpoint 用 Redis / SQLite；大模型用 Qwen2.5-7B + vLLM；工具接入用 MCP；测试评测是 pytest + Golden/Batch 跑批；部署用 Docker Compose。我最熟的是 Agent 后端、RAG、状态管理和评测。

## 8. 数据库和导诊记录怎么做？

**问（还原，录音较含混）：** 数据库这块是你做吗？保存什么数据？

**答（整理）：** 数据库由我构建。每次导诊结束后，会保存导诊记录、是否成功推荐科室以及相关状态数据，便于后期回溯。

**评分：6.0 / 10** — 有留痕和回溯意识，但未讲 schema、写入时机、失败隔离与医疗数据安全。

**参考答法：**

> 导诊状态和审计记录分开。多轮会话通过 LangGraph Checkpoint 保持；一次导诊结束、拒答或低置信结束时，清理当前槽位，并将完整导诊周期异步写入 SQLite 记录库。主要保存输入、路由、节点轨迹、候选科室、置信度、最终结果和错误状态，用于 badcase 回溯。落库失败不阻断用户主链路，患者数据还要做最小化存储和权限控制。

## 9. 大模型在链路中具体做什么？

**问（还原）：** 你们这个模型具体怎么用？

**答（现场整理）：**

1. **实体提取**：从用户的话里提取症状、部位等内容，写入槽位表。  
2. **置信度评分**：得到候选科室后，评估科室与用户问题的相关程度；现场口述为 0–10 分、6 分通过。

**评分：6.0 / 10** — 有明确任务边界，但与本仓实际实现存在两个口径风险。

**口径校正：**

1. 本仓 `dept_confidence` 是 **0–100 分，阈值 60**，不是 0–10 分。  
2. LLM 不只有两处；还可出现在 decision、症状澄清、科室消歧和最终回答生成等受限节点。  
3. 科室不由 LLM 直接决定；先由检索/规则得到候选或锁定结果，LLM 置信度只是门禁。

**参考答法：**

> LLM 被限制在几个明确节点：意图和实体结构化、信息不足时的澄清、候选科室消歧、以及科室与槽位的置信度评分。科室结论不由模型自由生成，而是由知识库和规则先锁定；置信度是 0–100 分，达到 60 才能继续，否则走固定拒答。这样做是为了不让模型直接「猜科室」。

## 综合评价

### 优势

1. **项目边界诚实**：没做小程序前端、没做微调，都没有强行包装。  
2. **有完整交付视角**：能说到 0→1、私有化、验证、交付和记录回溯。  
3. **知道模型不应直接包办结论**：把实体提取和置信度作为受限任务，方向正确。  
4. **技术经历与仓库大体对得上**：LangGraph、Python、RAG、槽位、科室消歧和记录落库均有代码/文档支撑。

### 短板

1. **口播不稳定**：Agent、LangGraph、槽位、置信度等核心词粘在一起；Qwen2.5-7B 被听成「2.57B」。  
2. **技术栈严重缩水**：实际项目比现场说的丰富，但面试官只听到 Python + LangGraph。  
3. **「我做的」多，「怎么做」少**：RAG、数据库、私有化均没给出具体契约或产出。  
4. **技术口径不严谨**：RAG 不是微调的通用替代；置信度实现是 0–100 / 60 分门禁，不是 0–10 / 6 分。  
5. **没有指标支撑**：未说 Golden 450、科室 ≥90%、急诊 100%、Batch100 等可证明「7B 够用」的结果。  
6. **无反问**：未确认岗位是偏小程序全栈、Agent 后端还是模型算法，无法针对性展示能力。

### 岗位匹配判断

| 假设岗位重心 | 匹配度 | 判断 |
|--------------|--------|------|
| Agent / LLM 应用后端 | 中上 | 项目链路匹配，但现场没讲出深度 |
| RAG / 知识库工程 | 中等 | 有实现，但本场证据很弱 |
| 微信小程序全栈 | 偏低 | 明确没做过小程序前端 |
| 大模型训练/算法 | 低 | 无微调、分布式训练等经验 |
| 测试/评测工程 | 高但未展示 | 简历与仓库强，本场完全没讲 Golden、pytest、Batch |

**结论：** 如果犀浦医疗岗位是 **Agent 后端 / LLM 应用落地**，候选人的实际项目能力高于本场表现；如果岗位要求 **小程序前端或底模训练**，则存在明显硬缺口。

### 下一轮优先补六件事

1. **背熟 60 秒自我介绍**：年限 → 定位 → 架构 → 个人责任 → 指标，不在开场展开全链路。  
2. **统一模型口径**：「Qwen 2.5，7B 参数，vLLM 私有化」，每个部分停顿。  
3. **统一置信度口径**：0–100 分，`score >= 60` 通过，低于 60 固定拒答。  
4. **准备 RAG 三分钟深挖**：数据→mapping→embedding→hybrid query→rerank/规则→降级→评测。  
5. **准备一个生产故障故事**：例如槽位污染、MCP 超时或 embedding 失败回退，按「现象—定位—修复—回归」讲。  
6. **反问岗位边界**：「这个岗位更偏 Agent 后端、小程序全栈，还是模型训练？」避免用错方向介绍自己。
