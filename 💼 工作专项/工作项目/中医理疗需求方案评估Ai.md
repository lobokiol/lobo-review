# 一、推荐选型

## 1）整体技术路线

建议采用下面这个架构：

输入层
TTM 报告 / 问诊文本 / TTM+问诊 / 后续 CT、生化、穿戴数据

-> 解析与标准化层
OCR/表格解析 + 症状/评估项抽取 + 同义词归一 + 严重度评分

-> 规则与召回层
知识库召回 + 规则匹配 + 优先级排序 + 方案融合 + 安全校验

-> 生成层
大模型负责：

- 理解用户自然语言
- 追问补充信息
- 把规则结果组织成“像 AI 生成”的自然语言输出

-> 反馈闭环层
记录输入、匹配路径、输出、人工反馈、疗效反馈、设备数据

------

## 2）我建议的具体选型

### A. 大模型选型

### 推荐定位

第一阶段不要训练模型，直接用现成中文大模型 API 或私有部署模型即可。

### 推荐用途

大模型只负责 4 件事：

1. 问诊文本理解
2. TTM/报告内容转结构化要点
3. 匹配不足时自动追问
4. 最终方案的语言润色和解释

### 推荐模型

如果走云 API：

- 通义千问 / Qwen 系列：中文医疗健康场景表达较自然，适合问诊、总结、追问
- 备选：DeepSeek 系列、GLM 系列

如果走私有化：

- Qwen 14B/32B 级别做第一阶段足够
- 不建议一上来就上超大模型，成本和维护不划算

### B. 向量库选型

文档里写“主要基于向量数据库/知识库完成匹配召回”，这个方向可以有，但不应该是主决策引擎。

### 推荐方案

- PostgreSQL + pgvector
- 小规模起步完全够用，简单、便宜、好维护
- 现在只有 8-12 个优先病症、20-30 个穴位、48 个方案目标，根本没必要一开始就上 Milvus/ES 的复杂集群

### C. 知识库/规则库选型

### 推荐实现

结构化知识库 + 配置化规则引擎，多个实体的命中确定最可能的方案

建议用：

- PostgreSQL 存主数据

- JSON/YAML 配置规则 存匹配规则、融合规则、追问规则

- 后端服务读取规则执行

  

### D. 报告解析选型

TTM 报告如果是 PDF/图片，建议单独做解析模块。

### 推荐

- PaddleOCR / MinerU / Docling 这类 OCR + 文档解析方案
- 如果 TTM 报告格式固定，优先用模板解析 + OCR 兜底

### E. 后端与工程架构，

如果没历史包袱，我建议：

- Python + FastAPI
- PostgreSQL
- pgvector
- Redis（缓存、会话态、追问上下文）
- 对象存储（报告文件、原始图片）
- 管理后台（方案库维护、规则调整、审核）

### F. 评测与监控

这个项目核心指标方案专家通过率和召回率，响应时间。

建议配：

- 日志追踪
- 每次匹配链路记录
- 方案版本记录
- 人工审核反馈
- 线上 badcase 收集

关键指标建议监控：

- 症状抽取准确率
- 健康问题 Top1/Top3 命中率
- 追问触发率
- 追问后命中提升率
- 方案专家通过率
- 不安全输出率

# 二、我对需求的问题

### 问题 1：不能把“向量库”当成核心方案引擎

向量库只能做召回，不能做最终决策。

### 问题 2：当前只有 1 套抗炎全身焕活方案

文档里说：

- 当前只有 1 套抗炎全身焕活方案，但方案一期需要很多
- 更多方案的推理数据案例未发现，比如说什么症状/数据得到什么方案

# 三、推荐实施计划

我建议分 4 个阶段做，而不是一上来把所有东西一起做。

## 阶段 0：需求固化与知识建模

这是最关键的一步，没做好，后面全是返工。

### 目标

把“专家脑子里的经验”变成机器可执行结构。

### 要做的事

1. 定义标准术语体系
   - 症状
   - 评估项
   - 健康问题
   - 病症
   - 穴位
   - 部位
   - 三期方案
   - 注意事项/禁忌
2. 选第一批 8-12 个病症
   每个病症都要形成标准模板
3. 明确 20-30 个允许穴位
   包含：
   - 标准名称
   - 别名
   - 所属部位
   - 取穴说明
   - 坐姿/卧姿差异
   - 身高体重修正逻辑
4. 定义匹配评分机制
   包括 80% 阈值和追问触发逻辑
5. 定义融合规则
   多问题怎么合并成 4/8 个部位
6. 建立首批验证样本集
   用于离线评测和验收

## 阶段 1：MVP 上线（TTM / 问诊 / TTM+问诊）

### 目标

先把“第一阶段需求闭环跑通”。

### 核心能力

1. 解析 TTM 报告
2. 解析问诊文本
3. 融合两类输入
4. 提取 Top3 健康问题
5. 映射到对应方案
6. 将多个问题压缩成 4 或 8 个部位
7. 输出一期/二期/三期结构化方案，先一期，二三期只做mock
8. 低置信度时自动追问
9. 记录每次匹配链路和结果

### 第一阶段建议范围

只做：

- 8-12 个高频病症
- 固定 20-30 个穴位
- 固定输出模板
- 明确的追问策略

### 阶段验收标准建议

- 能稳定处理 3 类输入
- 专家抽检通过率达到可上线水平
- 追问逻辑可用
- 输出结果可解释
- 每个结果能回溯“为什么这么出”

## 阶段 2：多源输入扩展

### 目标

扩到 CT、生化、穿戴设备等多参数输入。

### 核心能力

1. 各类报告解析模板化
2. 多源指标归一化
3. 多源证据融合评分
4. 输出 3-5 个核心问题
5. 接续第一阶段规则生成方案

### 重点

这一阶段不是“新增一个模型”就完事，关键是：

- 多种数据格式标准化
- 指标与问题的映射规则
- 冲突数据怎么处理

## 阶段 3：反馈闭环与优化

### 目标

做持续优化，但保持可控。

### 建议做法

1. 收集疗效反馈
2. 收集设备运行数据
3. 收集人工修正记录
4. 做权重优化和 rerank
5. 持续扩充方案库到 48 种

### 不建议

- 不要直接让模型自动修改知识库
- 不要直接用少量反馈做端到端训练

### 推荐方式

- 人工审核 + 数据闭环
- 规则阈值迭代（neo4j体量太大和复杂，用不到，数据库规则匹配就够了）
- 方案排序优化
- 高质量样本积累后再评估微调

## 阶段 4：合规与对接上线

### 目标

适配医院/机构接入和正式场景，脱敏数据。

### 要点

- 合规文本
- 免责声明
- 审批流程
- 日志审计
- 接口标准
- 数据权限和留痕

# 四、我建议客户现在就确认的关键问题

下面这些如果不先确认，后面会频繁返工。

## 1）业务定义类

1. 这个系统最终是“调理建议系统”还是“治疗方案系统”？
   这会直接影响合规措辞和输出边界。
2. 输出对象是谁？
   - 医生/理疗师/技师
   - 终端用户
   - 客服顾问
     不同对象，输出语言和严谨程度完全不同。
3. 第一阶段上线场景是什么？
   - 内部辅助工具
   - 门店技师使用
   - 用户端直接看到结果
   - 医院/互联网医院接口

------

## 2）医学/方案规则类

1. 第一批 8-12 个病症具体是哪几个？
2. 每个病症是否已有确定的三期方案？
3. 20-30 个允许穴位的清单是否已经定稿？
4. 是否存在绝对禁忌或高风险人群限制？

------

## 3）输入数据类

1. TTM 报告的格式是否固定？
2. 是否有多个设备厂商、多个报告模板？
3. 能否提供真实脱敏样本？
4. 是否已有标准问诊问题库？

------

## 4）算法评估类

1. 谁来做专家审核？
2. 追问后仍不足，是输出保守方案还是拒绝输出？

------

# 五、客户需要提供的材料清单

这个部分我给你列成最实用的清单，拿去就可以跟客户要。

## A. 方案知识材料

1. 第一批 8-12 个病症清单
2. 每个病症的三期标准方案
   - 一期/二期/三期目标
   - 穴位/部位
   - 频次
   - 周期
   - 注意事项
3. 48 个病症的总目录
4. 病症之间的优先级规则
5. 多病症融合规则
6. 禁忌症/风险规则

------

## B. 穴位与部位材料

1. 20-30 个允许穴位清单
2. 每个穴位的：
   - 标准名称
   - 别名/同义词
   - 所属部位
   - 定位描述
   - 使用限制
3. 部位与穴位映射表
4. 4/8 部位输出规则
5. 坐姿/卧姿/身高体重修正规则

------

## C. 输入样本材料

1. TTM 报告样本
   - 最少每种模板 20-30 份脱敏样本
   - 原始 PDF/图片 + 如果有结构化字段更好
2. 问诊文本样本
   - 真实用户表达
   - 专家整理后的标准结果
3. TTM+问诊联合样本
4. 第二阶段需要的：
   - CT 报告样本
   - 生化指标样本
   - 穿戴设备数据字段说明

------

## D. 标注与验收材料

1. 金标准样本集 即：输入 -> 专家认可的标准输出

2. 每个样本最好包含：

   - 输入原文/原报告
   - 提取出的症状/评估项
   - Top3 问题
   - 最终方案
   - 置信度判断
   - 是否需要追问

3. 验收标准文档

    

   例如：

   - Top1 命中率要求
   - 方案专家通过率要求
   - 追问准确率要求
