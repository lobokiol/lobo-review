### 5. 医院导诊项目的整体架构是什么？

**你的回答要点**

- 输入症状后先做实体提取和槽位门禁。
- 急诊规则优先处理。
- 疾病链走结构化知识库和 ES。
- 症状链走俗语归一、RAG、科室候选和科室消歧。
- 低置信度时让模型追问，最后根据置信度决定推荐或拒答。

**建议标准说法**

> 一次请求不是直接交给大模型生成答案，而是经过四层控制：第一层是输入和槽位门禁，确认至少有可处理的症状或疾病；第二层是安全护栏，先判断急诊红旗；第三层按 disease、symptom、reject 三路分流，疾病走结构化 KB，症状走 BM25+kNN 混合检索和科室规则；第四层是置信度和多轮澄清，候选不明确时最多追问 3 轮，仍不确定就固定拒答。LangGraph 负责状态和循环，LLM 只在实体抽取、澄清和置信度节点使用。

### 7. 查询不精准时通常是什么原因？怎么解决？

**你的回答要点**

- 知识库不完整或关键字缺失，例如俗称和标准医学术语不一致。
- 召回到错误片段后，后续推荐会偏掉。
- 增加置信度评分，低于阈值就拒答或兜底。
- 将 bad case 记录到数据库，和业务专家评审后维护知识库。

**建议答案**

> 我会先区分问题发生在哪一层：输入归一化、实体抽取、召回、规则打分、模型澄清还是最终生成。比如“脚脖子痛”可能召回到“颈部疼痛”，这不是简单增加 Prompt，而是要补充俗语归一和别名映射，并增加身体部位一致性校验。召回结果与原问题冲突时，置信度节点必须阻断错误推荐；同时记录 query、召回片段、候选科室、最终结果和用户反馈，经过业务专家评审后再更新知识库和回归集。

### 8. 你怎么做 Harness 工程？

**你的回答**

- 每个需求配单元测试。
- 自己构造冷启动数据，覆盖症状、疾病、急诊等类别。
- 用 Golden Dataset 和批量用例评测路由、实体和推荐结果。

**评价**

回答有真实内容，但没有先定义 Harness。建议统一回答：Harness 是包在模型外面的控制、评测和可靠性层，用来约束模型输入输出、执行流程、异常降级和结果验证。

**建议答案**

> 我的 Harness 分四部分：Agent Harness 负责状态机、节点边界和人工澄清；Eval Harness 负责 Golden Set、Batch Eval、指标和错误样本；Test Harness 负责单元、接口和回归测试；Reliability Harness 负责超时、主备模型、Checkpoint 回退和拒答。这样模型只是流程中的一个组件，不能直接越过安全规则产生最终结果。

### 9. Workflow 和 Agent 的区别是什么？

**你的回答情况**

回答不够稳定，主要提到目标、循环和定时任务，没有给出清晰区分。

**建议答案**

> Workflow 是预先设计好的流程，节点、顺序和分支基本确定，适合规则明确、可测试和可审计的任务。Agent 是模型根据目标、工具和当前状态动态决定下一步，适合路径不确定、需要规划和工具选择的任务。实际项目通常是混合方式：确定性的鉴权、急诊判断、检索和阈值判断用 Workflow；需要理解用户意图、生成澄清问题或选择工具的部分使用 Agent。医疗导诊项目的主骨架是 Workflow，局部节点才具有 Agent 特征。

### 10. Dify、Coze、Workflow 和 Agent 怎么选择？

**你的回答要点**

- Dify/类似平台适合快速做 Demo。
- 协作、版本管理和复杂流程维护可能不方便。
- 代码工作流稳定可控，但复杂流程建设成本更高。

**建议答案**

| 场景 | 选择 |
|---|---|
| 几小时验证需求、业务方需要快速看到效果 | Dify/Coze/低代码工作流 |
| 流程稳定、节点明确、需要可测和可审计 | 代码 Workflow |
| 需要动态规划、工具选择和多轮处理 | Agent，且要设置边界 |
| 企业内部小需求、周期只有几天 | 先用最小可行链路验证价值，不直接建设重型平台 |

### 11. 你对 Skill 的理解是什么？有没有实际使用？

**你的回答**

- 把同事的一套工作方法提炼成 Skill。
- Skill 类似 SOP，包含输入、输出、提示词、脚本和执行步骤。

**建议答案**

> Skill 不是一句 Prompt，而是一个可复用的任务能力包。它至少包含触发条件、输入格式、约束规则、执行步骤、可调用工具或脚本、输出格式和验收标准。比如简历初筛 Skill：输入简历和岗位要求，先抽取教育/技能/年限，再按业务确认的规则评分，输出匹配项、风险项和需要人工确认的问题，并保留证据片段。没有验收标准和业务边界的 Prompt，不能称为成熟 Skill。

### 12. 如何用轻量方案解决一个只给一周时间的业务问题？

**面试官重点**

面试官反复强调：FDE 不一定每次都搭建完整 Agent，需要判断业务真实诉求，选择脚本、规则、RAG、Workflow、Agent 或产品化改造中最轻的方案。

**建议回答框架**

1. 先访谈业务，确认痛点、频率、输入、输出和成功标准。
2. 估算人工耗时和错误成本，判断是否值得自动化。
3. 先选择最小方案：结构化抽取 + 规则/检索 + 人工确认，而不是默认多 Agent。
4. 用一小批真实脱敏样本做基线，确认准确率和失败类型。
5. 输出可追溯结果，所有高风险判断保留人工审核入口。
6. 一周内交付可运行 Demo、评测结果和下一步迭代清单。

### 13. 如果做“简历初筛 Agent”，你会怎么设计？

**你的回答要点**

- 先做实体抽取，识别年龄、学历、技能和关键字。
- 与业务部门沟通硬性门槛。
- 分模块评分，用简历和岗位问题做相似度匹配。
- 需求会变化，后续需要维护。

**建议答案**

> 我不会先做一个直接淘汰候选人的黑盒模型。第一步和 HR 确认硬性条件、加分项、风险项以及必须人工判断的部分；第二步把简历解析为结构化字段，并保留原文证据；第三步用规则处理硬门槛，用模型做语义匹配和问题生成；第四步输出评分、依据和不确定项，由 HR 确认后再进入下一步。历史录用数据不能直接当成绝对标准，需要检查过去的标准是否变化，并建立版本化规则和回归样本。

### 14. 医疗长文本病例智能校验项目解决什么业务问题？

**你的回答要点**

- 处理 2000-10000 字的长病例。
- 抽取疾病、手术、药物、检查和时间线。
- 发现病例之间的冲突，绑定原始证据。
- 医生最终审核，系统不直接修改医学事实。

**建议答案**

> 这个项目的核心价值不是“生成一份医学摘要”，而是减少医生整理多年病史和核对矛盾记录的时间。系统将长文本拆成带来源的医疗事件，重建时间线，识别药物、疾病、手术和检查记录之间的冲突，并把每个结论绑定到原始证据。AI 只负责抽取、归纳和提示冲突，医生确认后才进入正式记录。若项目尚未真实上线，必须明确说是方案/POC，不要说成已完成生产项目。

### 15. SSG 自然语言问数项目做了什么？价值是什么？

**你的回答要点**

- 业务人员通过自然语言查询订单等数据。
- 连接数据仓库和大表，通过语义理解生成查询。
- 参与 Pipeline、接口和批量验证。
- 后期工作较多是维护和响应。

**建议答案**

> 业务人员原来需要理解数据表和字段口径，才能查询季度订单、未完成订单等数据。我参与了从自然语言理解、指标映射、Spark/SQL 生成到结果格式化的 Pipeline，并开发批量验证插件，将逐条人工回归从 2-3 小时压缩到 30 分钟以内。这个项目中我也认识到，问数系统最难的不是生成 SQL，而是指标口径、表路由、权限和结果验证。

不要把后期维护讲成“没事做”，可以说成：项目上线后进入稳定运营阶段，负责知识更新、问题响应和结果质量维护。

### 16. 你展示的医院导诊 Demo 为什么会出现错误推荐？

**面试官实际反馈**

- 输入“腿痛”时推荐到中医科，面试官认为不合理。
- 用户只输入简单症状时，系统没有主动追问年龄、持续时间、位置、严重程度等关键信息。
- UI 和交互较简单，缺少面向患者的引导。

**这是本场最重要的失败点。**

**现场应该这样回答**

> 这个结果暴露出当前 Demo 的两个问题：第一，知识库或科室规则对身体部位和科室匹配不够严格；第二，输入信息不足时系统应该先进入澄清，而不是直接推荐。正确做法是把“腿痛”识别为信息不足，先追问具体部位、持续时间、是否外伤、是否肿胀麻木等，再基于候选科室和红旗规则判断。当前项目的重点是 Agent 工程链路，但这个 Demo 反馈说明产品层还需要继续迭代，我会把它作为 bad case 加入回归集。

不要辩解“这也可以”，要承认问题、定位原因、说明修复方案，并明确医疗系统的安全边界。

## 四、面试中需要立即改正的表达

| 问题 | 原表现 | 改法 |
|---|---|---|
| 过度技术化 | 反复讲 Harness、节点和数据库 | 先讲业务问题、用户、结果，再讲技术 |
| 项目边界不清 | “整个架构都是我做的” | 明确本人负责后端 AI，前端和业务由同事负责 |
| 价值不够具体 | 只说做了 RAG、MCP、评测 | 说明节省时间、降低错误、减少人工咨询或提升交付效率 |
| Demo 问题处理弱 | 试图解释错误推荐也合理 | 直接承认问题，提出信息收集、规则校验和回归修复 |
| 轻量化能力不足 | 默认用完整 Agent/Harness | 先做最小链路：抽取 + 规则/检索 + 人审 |
| 项目真实性风险 | 病例项目指标非常完整 | 明确真实项目、POC、设计方案的边界 |
| 概念回答不稳定 | Workflow/Agent/Skill/ReAct 混淆 | 使用“定义—适用场景—项目例子—取舍”四步回答 |
| 口头表达含糊 | “差不多、比较复杂、后面处理” | 用“问题—动作—结果—复盘”表达 |

## 五、面试后的固定回答模板

### 项目题

> 这个项目服务的用户是……，原来的痛点是……。我负责……，团队其他成员负责……。我选择……而不是……，原因是……。上线/验收前通过……验证，结果是……。目前仍存在……，下一步会通过……修复。

### 轻量化方案题

> 我先确认问题是否高频、是否有明确输入输出、人工成本是多少。若规则能解决，就不直接上 Agent；若需要语义理解，先用结构化抽取加规则或检索；只有路径不确定、需要工具选择时才引入 Agent。第一周交付小样本 Demo、评测结果和人工审核闭环。

### 结果不可靠题

> 先判断是数据、召回、规则、模型还是交互问题；对高风险结果不直接执行，必须保留证据、阈值和人工确认；把 bad case 加入回归集，修复后重新评测。

## 七、最终判断

这场面试不是单纯考察你会不会 LangGraph，而是在判断你能不能把 AI 技术转成业务部门愿意使用的解决方案。当前优势是工程底子和后端 AI 实现能力；主要短板是业务价值表达、轻量化方案选择、产品交互和 Demo 质量。下一阶段不宜继续堆技术名词或新项目，优先把现有项目做出一个真实、清楚、可验证的业务闭环。
