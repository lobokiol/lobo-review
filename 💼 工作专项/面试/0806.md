## 一、JD 要的人

这个岗位要的不是纯算法研究员，也不是只会调用大模型 API 的开发，而是：

> **能把模糊需求独立做成可用产品的 AI-Native 全栈/产品型工程师。**

核心画像：

1. Python 或 TypeScript 工程基础扎实，能自己写代码和排查问题。
2. 有 Claude Code 或 Codex 的真实项目经验，不只是聊天和复制代码。
3. 懂 ReAct、Plan-and-Solve、Tool Calling、Memory 和 Agent Loop。
4. 了解 LangGraph、Dify、AutoGPT 等框架，有二次开发经验更好。
5. 可以覆盖“需求分析 → 产品设计 → 技术方案 → AI 协同编码 → 测试 → 交付”的完整闭环。
6. 在小团队中高自主工作，能直接和业务方、产品人员对需求。
7. 拒绝“纯 PPT 架构师”，最终看实际代码和独立交付。

预估权重：

| 能力 | 权重 |
|---|---:|

## 三、面试问题清单

### 1. 之前公司做的是什么项目？

**回答要点**

- 医疗项目，涉及病例筛查、医疗知识和 RAG。
- 使用 Python 开发，过去也有测试开发经验。

**复盘**

项目方向与岗位相关，但转写中项目的用户、业务价值、本人职责和量化结果没有形成简洁闭环。

### 2. 你写过 Java 吗？Python 和 Java 的并发模型有什么区别？

**现场表现**

回答了 Java 多线程可以利用 CPU，Python 偏事件驱动，但没有准确说明 GIL、CPU/IO 密集任务、`asyncio` 和多进程的边界。

**标准回答**

> CPython 的 GIL 会限制多个线程并行执行 CPU 密集型 Python 字节码，但不等于 Python 无法高并发。IO 密集任务适合 `asyncio` 或线程池，CPU 密集任务适合多进程、原生扩展或独立计算服务。Java 线程通常可以直接并行利用多核，但也有线程调度和上下文切换成本。应根据负载模型选择，不是简单判断谁更好。

### 3. 机试项目中，删除文件时先删文件还是先删数据库？

**面试官连续追问**

- 文件删除成功，数据库挂了怎么办？
- 数据库修改成功，文件删除失败怎么办？
- 数据库事务能不能回滚文件系统操作？
- 服务中途宕机怎么恢复？
- 长时间停留在“删除中”的记录怎么处理？

**现场表现**

开始回答“先删文件，再删数据库”，被追问后承认没有完整考虑。状态机、重试和补偿方案主要是面试官引导出来的。这是本场最明显的工程失分点。

**标准回答**

> 删除请求先在数据库事务中把状态从 `ACTIVE` 改为 `DELETING`。事务提交后，由异步任务删除文件。文件不存在也视为成功，保证幂等。成功后把状态改为 `DELETED`，失败则记录次数并重试。定时任务扫描长时间停留在 `DELETING` 的记录，进行补偿、对账或告警。数据库事务无法直接覆盖文件系统，因此采用状态机和最终一致性，必要时结合 Outbox、消息队列、软删除或对象存储版本。

### 4. 你用 AI 写代码多久？有哪些经验和坑？

**回答要点**

- 从去年 12 月左右开始深度使用 Claude Code 等工具。
- 不能一次性把大需求全部交给 AI，否则容易得到“看起来很美好”但不可靠的结果。
- 使用 SDD、Plan 和 Skill 先完成规划，再分步执行。
- 需求、实现和验证不能全部托管给 AI。
- AI 可能自己伪造数据，让测试“假通过”，必须人工检查真实链路。
- 顶级模型负责计划和审查，其他模型可以负责执行。

**复盘**

这是本场最强的回答，与 JD 中 Claude Code/Codex、Skill 和 AI-Native 开发经验高度匹配。

### 6. 你怎么看 RAG 和现在 Agent 渐进式搜索的区别？

**面试官的追问**

- Claude Code/Codex 没有把代码库全部向量化，为什么仍然可以理解代码？
- 长上下文或 Agent 主动读文件能不能替代 RAG？
- 两种方案在准确率、成本、速度和可评测性上有什么区别？
- 为什么传统 RAG 的召回率很难达到 100%？

**现场表现**

表达了“大模型上下文变大后，很多场景不一定需要 RAG”，但没有完整拆出 RAG、Tool Calling、Agent Loop 和上下文管理的边界，后续主要由面试官讲解。

**标准回答**

> RAG 是先从大规模语料中检索候选证据，再将证据放入上下文生成结果，适合大规模、低延迟和低成本检索。Agent 渐进式搜索由模型根据中间结果反复选择目录、文件和工具，适合代码库、结构化目录和需要多步判断的任务。长上下文和 Agent 搜索可以替代一部分简单 RAG，但不能普遍替代。Agent 搜索通常更灵活，但更耗 Token、延迟更高，路径也更难固定评测；二者可以组合使用。

### 7. Agent Tool Use 的本质是什么？

**现场表现**

这一题没有形成完整回答。面试官表达了“看来你对 AI Agent Tool Use 这套东西不是很了解”，随后解释了渐进式搜索。

**标准回答**

> Tool Use 的本质是模型根据当前目标和状态，输出结构化的工具名和参数；外部程序真正执行工具，再将 Observation 返回给模型。模型根据结果继续决策，形成 ReAct/Function Calling Loop。工程上还要约束工具权限、参数校验、超时、重试、最大步数、幂等和人工确认。

### 问题 2：你之前写过 Java 吗？

> 请按真实经历把“接触过 Java”改成“有生产项目经验”或“只做过基础学习”，不要夸大。

### 问题 3：Python 和 Java 的多线程/并发有什么区别？

**建议回答：**

> 要先区分 IO 密集和 CPU 密集任务。Java 多线程通常可以在多核 CPU 上并行执行，适合复杂的企业后端并发场景，但也要考虑线程调度、锁和上下文切换成本。CPython 受 GIL 影响，多个 Python 线程不能同时并行执行 CPU 密集的 Python 字节码，但线程对 IO 密集任务仍然有效。高并发 IO 场景我会优先考虑 `asyncio`；CPU 密集场景会使用多进程、任务队列、原生扩展或独立计算服务。所以不能简单说 Python CPU 利用率低，关键是根据负载选择并发模型。

### 问题 4：删除文件时，应该先删文件还是先删数据库？

**建议回答：**

> 我不会把这个问题简化成先后顺序，因为不管先做哪一个，第二步都可能失败。我会把数据库作为状态的事实来源，先在事务中将记录从 `ACTIVE` 改为 `DELETING`，提交后由后台任务删除文件。文件删除成功后改为 `DELETED`，失败改为 `DELETE_FAILED` 或保留 `DELETING` 并重试。整体通过状态机、幂等、重试和补偿来实现最终一致性。

#### 追问 4.1：文件删除成功，但数据库更新失败怎么办？

> 文件删除必须是幂等操作，后台任务可以继续重试数据库状态更新。对于长时间不一致的记录，由定时对账任务检查文件是否存在，如果文件已不存在，将数据库补偿为 `DELETED`。重试超过上限后记录告警，不能静默失败。

#### 追问 4.2：数据库状态更新成功，但文件删除失败怎么办？

> 记录保持 `DELETING` 或改为 `DELETE_FAILED`，用户端不再把它当成正常文件展示。后台任务按退避策略重试；超过次数上限时告警或转人工处理。如果业务要求可恢复，可先做软删除或利用对象存储版本提供回收站。

#### 追问 4.3：能不能把文件删除放进数据库事务？

> 不能直接实现原子事务。数据库事务只能保证数据库内部操作，无法回滚本地文件系统、对象存储或第三方网络服务。这类跨资源操作通常通过 Outbox、消息队列、Saga/补偿和定时对账实现最终一致性。

#### 追问 4.4：服务删除到一半宕机了怎么办？

> 状态已经持久化在数据库中，服务恢复后，Worker 或定时任务继续扫描 `DELETING` 记录。由于删除操作是幂等的，重复执行不会破坏系统。如果使用消息队列，则要处理至少一次投递带来的重复消费。

#### 追问 4.5：一条记录长时间是“删除中”怎么办？

> 记录开始时间、最后重试时间、重试次数和错误原因。定时任务扫描超时记录，核对文件真实状态：文件已不存在就补记为 `DELETED`；仍存在就继续重试或转 `DELETE_FAILED`。超过阈值后告警并进入人工处理队列。

### 问题 5：你用 AI 写代码多久了？

**建议回答：**

> 我从去年 12 月左右开始深度使用 Claude Code/Codex 做项目，不是只用它生成一个函数，而是用于需求分析、架构讨论、代码实现、测试和问题定位。我现在的基本流程是先了解现有代码和需求，写出可评审的计划或 SDD，和业务方确认取舍后再分步实现，最后由我自己检查差异、运行测试并验证真实数据链路。

### 问题 6：使用 AI 编码时遇到过哪些坑？

**建议回答：**

> 我遇到过三类典型问题。第一，一次性给出过大需求时，AI 会产生表面完整但内部假设很多的方案，所以要先分析和评审，再分步执行。第二，AI 可能为了让测试通过而伪造数据或 mock 掉核心依赖，例如本来要验证真实数据库，它却用本地数据让测试变绿。第三，AI 可能对现有架构和业务约束理解不完整，产生过度重构。我的处理方式是用规格约束输入，限制改动边界，人工审查 diff，并通过集成测试和真实环境验证结果。

### 问题 8：你怎么看 RAG 和 Agent 渐进式搜索的区别？

**建议回答：**

> 我认为两者不是简单的替代关系。RAG 通常会先对大量文档做索引，根据查询召回少量候选内容，再交给模型生成，优势是检索快、成本可控，适合大规模语料；问题是切片、索引和召回策略可能丢失关键证据。Agent 渐进式搜索不是一次检索完成，而是先读目录、索引或概要，再根据中间结果选择下一个文件或工具，直到收集足够证据。它对代码库和结构化目录很有效，但 Token 成本、延迟和不确定性更高。实际系统可以先用 RAG 缩小候选范围，再让 Agent 渐进核对关键证据。

#### 追问 8.1：Claude Code/Codex 没有把所有代码向量化，为什么还能理解代码库？

> 因为它不是一次把全部代码塞进上下文，而是借助文件列表、文本搜索、语法/符号信息和分步文件读取做渐进式定位。每次工具返回新的 Observation，模型再判断下一步读什么。本质上是工具调用和 Agent Loop，不是依赖单次向量召回。

#### 追问 8.2：Agent 搜索能完全替代 RAG 吗？

> 不能一概而论。数据量小、目录结构清晰、可以通过工具逐步定位时，Agent 搜索可能比单纯向量 RAG 更准。但对百万级文档、低延迟在线问答和成本敏感场景，仍然需要倒排索引、BM25、向量检索或混合检索快速缩小范围。更常见的是混合架构，而不是谁彻底取代谁。

#### 追问 8.3：如何评测两种方案？

> RAG 可以拆成检索和答案两层评测：检索层看 Recall@K、MRR和证据命中率，答案层看正确性、忠实性和引用证据。Agent 还要增加任务完成率、工具调用成功率、步数、Token 成本、延迟、失败恢复和路径稳定性。最终要用固定任务集对比质量、成本和响应时间，不能只看个别 Demo。

### 问题 9：Agent Tool Use 的本质是什么？

**建议回答：**

> Tool Use 的本质是，大模型不直接执行外部操作，而是根据当前目标、状态和工具描述，生成结构化的工具选择和参数。运行时执行工具，把结果作为 Observation 返回模型，模型再决定是继续调用工具还是输出最终结果。这会形成 ReAct 或 Function Calling Loop。工程上必须限制可用工具和权限，校验参数，设置超时、重试和最大步数，对写操作或高风险操作增加人工确认。

### 问题 10：ReAct、Plan-and-Solve 和 Workflow 有什么区别？

**建议回答：**

> ReAct 是边判断边执行，模型根据每次工具返回结果决定下一步，适合路径不确定的任务。Plan-and-Solve 会先拆出一个计划，再按步执行，适合多步且需要全局协调的任务。Workflow 的主要节点、路由和边界由开发者预先定义，可预测性和可评测性更强。生产系统通常是混合的：外层用 Workflow 控制边界，在少数需要动态判断的节点内使用 ReAct 或 Plan-and-Solve。

### 问题 11：Agent 的 Memory 是什么？

**建议回答：**

> Memory 不是单纯把所有历史消息都塞进 Prompt。短期记忆保存当前任务所需的对话、中间结果和工具状态；长期记忆保存稳定的用户偏好、事实或过去任务经验；任务记忆或 Checkpoint 用来恢复执行进度。工程上要考虑摘要压缩、检索、过期、隐私、权限和错误信息被长期固化的风险。
