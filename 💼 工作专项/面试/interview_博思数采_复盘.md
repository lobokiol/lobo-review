## 3. 17 个节点哪些最关键、为何这样设计

**问：17 个节点流程很长，哪些最关键？哪些可忽略？为什么这样设计？**

**答（整理）：** 以「肚子疼」为例说明主链路：

1. **预处理**：截断至约 200 字、错别字改写、停用词处理。  
2. **实体提取 + 意图识别**（曾分开，后合并）：抽取症状、疾病、年龄性别、急诊、持续时间、严重程度，写入槽位表，据此判意图。  
3. **四意图路由**：症状 / 疾病 / 急诊 / 特殊机制；多意图有优先级：急诊 > 疾病 > 症状 > 特殊机制；疾病与症状同级可都走，但有顺序。  
4. **症状链**：RAG 语义召回做俗语归一（「肚子疼」→「腹痛」）→ 位置追问（上/下/左/右腹）→ ES **关键词**检索（非向量）→ 关联症状多选，每选 +2 分加权 → 科室评分 → 置信度 ≥6 分才输出。  
5. 关键节点：预处理、实体+意图、RAG 归一、位置追问、关键词检索、多选打分、置信度门禁。

**评分：7.0 / 10**

| 维度 | 简评 |
|------|------|
| 技术准确度 | 业务逻辑对，但节点是泛称，未对齐仓库真实名 |
| 项目贴合度 | 缺 **条件边** 视角；「200 字截断」易被质疑来源 |
| 面试表达力 | 分点清楚，口播重复多；未解释「为何 17 节点而非单 Prompt」 |

**点评：** 面试官要的是 **状态机设计决策**。应映射到 `trim_history` → `decision`+`slot_fill` → `emergency_gate` → `slot_gate` → 三路由。

**参考答案（结合 `app/graph/builder.py`）：**

> 17 个节点一张图讲完，最关键 **三条条件边**：  
> 1. **`emergency_gate`**：急诊硬规则命中 → 直接 `answer_generate`，不进普通消歧。  
> 2. **`slot_gate`**：主症/主病至少一项，否则 `reject` 追问。  
> 3. **三路由**（`route_after_slot_gate`）：`disease_dept` / `rag_symptom_recall` / `reject`。  
> 症状链：`rag_symptom_recall` → `symptom_clarify`（≤3 轮）→ `dept_rules_disambiguation` → `dept_confidence` → `fetch_oncall` → `answer_generate`。  
> 设计原因：导诊要 **可回归、可追责、可拒答**，不是单次 ChatCompletion。

## 4. 槽位设计 & 单/多分类

**问：槽位怎么设计？每种症状都有槽位吗？是做分类吗？单分类还是多分类？多意图会并发吗？**

**答（整理）：** 槽位服务意图识别，抽通用字段（症状、疾病、年龄性别、急诊、持续时间、严重程度），不是每症状一套。多值意图识别；不并发，按优先级：急诊 > 疾病 > 症状 > 特殊机制；疾病与症状可都触发，有执行顺序。

**评分：7.5 / 10** — 「通用字段」正确；未说明 `SlotTable` + `slot_gate_passes` 与 `triage_route` 三分类（disease/symptom/reject）。

**参考答案：**

> 槽位是 `SlotTable` 通用字段，由 `decision`+`slot_fill` 写入，`slot_gate` 判断是否够格。意图层 `IntentResult.triage_route` 输出 **disease / symptom / reject**；`emergency_gate` 关键词硬拦截。多信息并存按条件边顺序走，不是多 Agent 并发。

## 5. 症状长链路如何防漂移

**问：症状链很长，如何保证不越走越偏？**

**答（整理）：** 强规则约束。RAG 把口语归一到标准词（腹痛），再位置追问锁定（右腹痛等），之后走 ES 关键词检索而非自由发挥；候选科室后关联症状多选加权评分得最终推荐。

**评分：8.0 / 10** — 与 `symptom_clarify` → `dept_rules_disambiguation` → `dept_confidence` 高度一致；可补 `rag_miss_reject` 与澄清轮次上限。

**参考答案：**

> 防漂移三段锁死：  
> 1. `rag_symptom_recall`：BM25+kNN 归一俗语。  
> 2. `symptom_clarify`：知识库配置维度出 **选项卡**，轮次有上限。  
> 3. `dept_rules_disambiguation` + `dept_confidence`：规则打分，低置信 `low_confidence_reject`。  
> LLM 只用于澄清文案和置信评判，科室锁定靠规则表。

## 6. MCP 作用、开发内容与踩坑

**问：MCP 和直接调 HIS 的区别？做了哪些改造？开发 MCP 要做哪些事？遇到什么问题？工具调用准确率如何？**

**答（整理）：**

- **作用**：科室推荐成功后，通过 MCP 自动拉未来三天预约信息推给用户，减少手工步骤。  
- **开发**：建 MCP 服务/客户端，封装工具，调院内系统。  
- **问题**：下游服务更新后召不回；有时返回空；曾出现死循环/重复调用；加判空，空结果不展示。  
- **准确率**：路径较固定，通过结构化结果触发 MCP，非自然语言临场选工具，故命中问题不大。

**评分：6.5 / 10**

| 维度 | 简评 |
|------|------|
| 技术准确度 | 角色偏笼统；仓库分 **`fetch_oncall`** 与 **`mcp_followup`** |
| 项目贴合度 | 未提 Stdio、`McpHospitalClient`、`list_tools` 缓存 |
| 面试表达力 | 排障真实，实现细节薄 |

**参考答案：**

> MCP 是 **医院工具适配层**，非 ReAct 自由选工具：  
> - `fetch_oncall`：科室锁定后调 `get_oncall_appointments`。  
> - `mcp_followup`：规则识别「科室介绍/路线」→ `get_department_intro` / `get_department_route`。  
> `app/mcp/client.py` 用 MCP Stdio 拉起 `hospital_mcp/server.py`；下游空返回做 graceful degrade。命中率高因 **节点级固定触发**。

## 7. Agent 过程正确性 & 节点级排障

**问：怎么评估 Agent 过程是否正确？17 个节点错了怎么定位？Golden Case 怎么构建？跑批后怎么判断是流程还是知识库问题？**

**答（整理）：**

- **过程评估**：看召回、追问、最终科室是否一致；置信度调查不只看问答结果，还看与候选科室匹配度。  
- **排障**：① 类 LangSmith 可追溯——每节点输入/输出/时间；② SQLite 落库，以「是否成功推荐科室」组织会话，批凉统计 Bad Case。Golden 来自现场反馈，按急诊/疾病/症状/多轮/闲聊/敏感等分类，标注目标科室，约 450 条；每次改需求跑一轮回归。  
- **流程 vs 知识**：流程靠节点追溯；知识靠现场标注核实；初期有 AI 造数，后期换现场数据；需标注人员持续反馈迭代。  
- **排障谁看**：主要自己看；承认 17 节点手工排查耗时。

**评分：7.5 / 10** — 思路对；应少说「类似 LangSmith」，多说 `triage_recorder` + `node_trace` + `classify_outcome`。

**参考答案：**

> 1. **链路一致性**：追问选项来自当前 `rag_chunk`；锁定科室与 `dept_rules` 一致。  
> 2. **节点日志**：`>>> Enter node: xxx` + `chat_service` 返回 `node_trace`。  
> 3. **落库**：`triage_recorder` 写 SQLite，含 `ner_result`/`slot_table`/`dept_state`/`rag_chunk_id`、`classify_outcome`。  
> Bad Case：先看 outcome，再比快照——定位 **路由 / 召回 / 打分** 哪层坏了。

## 8. Bad Case 迭代会不会污染知识库

## 9. 上线后用户反馈与迭代

**问：上线了吗？用户反馈如何？**

**答（整理）：** 已上线小程序。主要问题与改造：

1. **追问过多、成本高** → 改选项卡，用户只自由输入一次症状，其余点选。  
2. **年龄性别反复问** → 前置问人卡，一次写入槽位。  
3. **高频重复问** → Redis FAQ 缓存一天（同症状当天不走完整检索）。  
4. **状态污染** → 科室推荐结束（无论成败）清空上一轮 LangGraph 状态，避免「肚子疼」影响下一轮「脚踝疼」。

**评分：8.0 / 10** — 产品化思考好；FAQ 缓存在开源仓未体现，被追问需能说出 key 设计。

**参考答案：**

> 1. `symptom_clarify` / `dept_rules_disambiguation` 返回 `last_choices`，前端点选。  
> 2. 年龄性别一次写入 `slot_table`。  
> 3. 导诊结束 `session_reset`：保留 `messages`，清空 `slot_table`/`dept_state`。  
> 改动效果用 Golden 回归量化。

## 10. 评测指标如何计算

**问：生产评测和开源评测指标怎么算出来的？意图路由节点为何单独设计？准确率/召回率有区分吗？**

**答（整理）：**

- **CI**：每次需求补单测，纳入 CI 保回归。  
- **Batch**：自研 AI 生成+人工整理用例，要求稳定通过。  
- **生产 Golden**：现场数据波动大，持续验证修正。  
- **意图路由准确率**：约 100 条话术，标注意图，跑 `decision` 节点，预期 vs 实际，错误数/100。  
- **召回率**：意图节点主要说准确率，未单独区分召回。  
- **意图节点**：曾更多，后因「区分病了」等节点多余，精简到约 12 个；导诊台不可能看病，过多节点维护成本高。

**评分：6.0 / 10** — **本场最弱题之一**；简历数字（97%、80%、90%）未给出分子分母与脚本名。

**参考答案：**

> 三套固定口径：  
> 1. **pytest**：`tests/` 25+ 模块 merge gate。  
> 2. **Batch100**（`eval_round_common.py`）：**A** 推荐成功率 ≥80%；**B** 科室相关性 ≥70 分占比；路由 ~97% = `triage_route` 与标注一致率。  
> 3. **生产 Golden ~450**：科室 ≥90%，急诊 100%，误推 ≤5%。  
> 跑批：`run_medical_data_batch.py` → `build_medical_eval_table.py` → `eval_medical_batch.py` → `run_all_eval_rounds.py`。

## 11. 生产 vs 开源评测差异

**问：科室成功推荐评测，生产和开源方法差不多吗？**

**答（整理）：** 方法相近，差异在现场反例——科室映射会变（如脚痛原只有骨科，现场要加皮肤科）；科室名称持续更新，评测集也要跟新。

**评分：7.5 / 10** — 真实痛点；可补「生产 Golden 由医学顾问标，开源 Batch 用脚本 judge」。

**参考答案：**

> 开源 Batch100 重 **路由与链路完整性**；生产 Golden 重 **科室口径与现场变异**。科室映射变更走 `rag_department_rules` + 版本化 eval round，不混用两套标注标准。

## 12. 前端、模型与部署

**问：前端谁做的？用的什么模型？什么卡？并发多少？每轮耗时？有没有思考模式/流式？**

**答（整理）：**

- 前端：同事做，自己主要负责演示；医院信息不能外泄。  
- 模型：**Qwen2.5-7B**（口述「签问十四笔/二达五」为 ASR 误识）。  
- 部署：双 **L40S 48G**，vLLM，评估约 **15 QPS** 常态、峰值约 30；p99 压测目标 30 QPS。  
- 耗时：整套导诊约 4s；**单轮用户感知**要求 <2s（非整轮）。  
- 思考模式：**没有**单独做思考/非思考模式。

**评分：7.0 / 10** — 有生产数字是加分项；思考模式/流式答「没有」略被动，可说明「结构化节点用 `structured_output`，回答节点可 SSE 但我们未上」。

**参考答案：**

> 生产 vLLM 双卡 Qwen2.5-7B-Instruct 主备，OpenAI 兼容接口 + prefix caching；`chat_once_async` 整体超时 60s。LLM 仅在 decision/澄清/消歧/置信度调用，故 7B 够用。流式可对 `answer_generate` 开 SSE，当前 Web 以整轮 JSON 为主。

## 13. 模型维护与选型

**问：还在持续维护吗？考虑过升 Qwen3 吗？选型时做过对比测试吗？**

**答（整理）：**

**评分：5.5 / 10** — 诚实但显薄弱；应用岗也应能讲清「7B 够用因为 LLM 只做抽取/澄清，科室靠规则」。

**参考答案：**

> 选型约束：数据不出院、Apache 2.0 可商用、院内信创。Qwen2.5-7B 在 slot 抽取与结构化澄清上 Batch 已够，科室决策不靠大模型生成。升 Qwen3 会用同一套 Golden 做 A/B：看 NER F1、澄清通过率、延迟，而不是凭品牌升级。

## 14. 其他项目 & 架构演进

**问：除导诊外还做过什么？一开始就用这套结构吗？**

**答（整理）：**

- 还有车蓄电池利废等小项目。  
- 导诊 **不是一开始就这样**：早期走「疾病大类 + 大量问询 + 疾病知识图谱 + 关键字检索融合」，维护难、准确率低，与上线要求差距大，后砍掉。  
- 第一版参考开源项目，但与现场差距大——开源推疾病序列、知识图谱第三方难改、症状-科室映射僵化。  
- 最终进化到：**症状 RAG + 规则打分 + 结构化槽位**，开源项目仅作参考。

**评分：8.5 / 10** — **本场最佳题之一**；有真实踩坑、有架构取舍，体现工程成熟度。

**参考答案：**

> 演进路径：疾病图谱方案 → 准确率低、不可维护 → 改为 LangGraph 显式状态机 + OpenSearch hybrid + `department_rules` 打分 + 低置信拒答。开源仓保留可演示核心链路，生产接 vLLM + 真 HIS。面试可对照 GitHub 现场跑 Batch100。

## 15. 岗位介绍 & 候选人回应

**问：这个岗位做什么？**

**答（面试官）：** 政府采购全流程智能化——从招标文件编制、需求文件编制到合规性检查、评标；当前重点 **合规性审查**，难点在长文档上下文；文档开头结尾一次性比对等，需要精巧的事先设计。

**问：你有没有相关问题？**

**答（候选人）：** 提到问询过程中可用「三明治」式上下文——每次拿文档摘要 + 上一轮问询统计 + 当前问题，类似其额外功能思路，表示可用这方面解决长文档问题。

**评分：6.0 / 10（岗位匹配回应）** — 有迁移意识，但过短、未展开 RAG 分块、引用溯源、规则+LLM 分层审查等你已具备的方法论。

**参考答案（投合规审查岗）：**

> 医疗导诊和政采合规表面不同，工程方法可迁移：  
> 1. **长文档**：章节分块 + 元数据（文号/章节/页码）入向量库，审查时「检索相关条款 + 摘要滑动窗口」，避免整本塞上下文。  
> 2. **合规规则**：硬性条款（资质/金额/截止时间）用规则引擎先筛，LLM 只做语义歧义与缺失项说明——同导诊里急诊硬规则 + LLM 澄清。  
> 3. **可追溯**：每次审查落库输入片段、命中条款、结论，方便人工复核——同 `triage_recorder`。  
> 4. **评测**：构建 Golden 招标文件 + 已知违规点，改 prompt/规则后回归，避免个例污染通用规则库。

## 综合评价

### 优势

1. **Agent 工程化完整度高**：能讲清状态机、槽位、急诊优先级、症状链规则锁定，不是只会调 API。  
2. **测试与评测基因**：Golden 450 条、分层 badcase、上线后四轮产品迭代（选项卡/问人卡/状态重置），符合「可评测系统」画像。  
3. **架构演进有说服力**：疾病图谱方案失败 → 规则+RAG 方案，体现取舍能力。  
4. **生产落地细节**：Qwen2.5-7B、双 L40S、QPS 与单轮延迟有数。  
5. **诚实**：简历笔误、节点排查耗时、模型未充分评测，不硬撑。

### 短板

1. **指标口径不稳**：97%、80%、90% 未与脚本/分子分母绑定，易被继续追问穿帮。  
2. **实现细节偏虚**：MCP、追溯、节点名与仓库文件对齐不够，显得「做过但说不清代码在哪」。  
3. **模型与推理模式**：选型缺乏对比实验；思考模式/流式未主动说明产品取舍。  
4. **岗位迁移表达弱**：博思数采 JD 是 **政务文档合规**，结尾仅一句「三明治上下文」，未系统映射 RAG/规则/评测经验。  
5. **表达**：转写显示口播重复、专有词混乱，现场听感可能打折扣。

### 与岗位匹配度

| 维度 | 医疗导诊项目 | 博思数采合规审查岗 |
|------|--------------|-------------------|
| 场景 | 多轮问诊、科室推荐 | 长文档、条款比对、合规规则 |
| 可迁移 | 状态机、检索、规则护栏、Golden、落库追溯 | 高度相关 |
| 缺口 | 无政采业务语料 | 需补文档分块、条款引用、审查 checklist |

**匹配结论**：工程能力 **中等偏上**，业务域 **需 1–2 个月熟悉**；若岗位重「Agent 编排 + 评测闭环」而非「政采专家」，可培养。
