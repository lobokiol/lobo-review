# NovelToVideo RAG 工程化面试题（100 题）

## 使用说明

按面试教练的追问路径回答：**做了什么 → 本人负责什么 → 为什么这样设计 → 考虑过什么替代方案 → 如何验证 → 哪里失败或仍不完善 → 条件变化后如何调整**。

回答项目事实时，区分三类内容：

- **代码已实现**：能指出当前代码位置，并说明输入、状态变化和输出。
- **已验证**：能提供可复现的测试、样本、日志或指标。
- **待建设方案**：能解释设计取舍，但不说成已上线或已验证。

若谈准确率、召回率、成本、延迟或节省时间，补充指标定义、基线、分母、样本量、测试条件，以及是绝对变化还是相对变化。没有实际数据时，明确说“尚未测量”，再提出最小评估方案。

## 当前代码事实卡

下面只记录核对过的实现事实；实际面试前仍应在自己当前分支复查。

| 主题 | 当前实现 / 边界 | 代码位置 |
|---|---|---|
| 检索路径 | 元数据精确命中可提前返回；事件 JSON 命中后可补关联章节正文；否则走向量与词法召回并用 RRF 合并；没有向量结果时走词法兜底 | backend/app/services/screenwriting/rag_index.py |
| RRF | 融合向量与词法排名，常数为 60；这不是 Cross-Encoder 重排，也不等于 BM25 | rag_index.py 中 _merge_ranked_hits |
| Context | 默认召回上限 50；索引 Chunk 默认 900 字符、重叠 120 字符；词法 fallback 文档片段最多保留前 1200 字符。未发现按生成模型 tokenizer 执行的总 Token Budget | backend/app/core/rag/constants.py、rag_index.py |
| Warm-up 执行 | 使用当前 API 进程内的 asyncio.create_task 和 _warmup_tasks 去重，不是 Redis Stream Worker；部分同步向量操作通过 asyncio.to_thread 执行 | backend/app/services/screenwriting/rag_runtime.py |
| 增量更新 | 有 Chunk 内容哈希、skip_unchanged 和过期 ID 清理；刷新直接修改现有索引，没有 V1/V2 staging 与 active-version 原子切换。中途失败可能留下部分新写入 | rag_index.py、rag_runtime.py |
| 刷新状态 | 指纹、任务引用和索引对象缓存保存在进程内；成功完成后才记录本进程的文档指纹。Chroma 数据本身持久化，但任务状态没有持久化到 Redis/MQ/数据库 | rag_runtime.py |
| 删除 | 项目、单章和批量删章的服务函数没有直接调用 RAG 清理。删章后的旧向量要等后续索引刷新才可能被清理；项目删除没有显式删除其 Chroma 项目目录 | backend/app/services/project.py、backend/app/services/novel.py |
| 证据与引用 | RAG Context 会格式化命中来源并加入提示词；未发现生成答案后的 Citation ID 校验、独立冲突裁决或 Evidence Gate | rag_index.py、rag_runtime.py |
| 评估 | 本题库中的 Golden Set、K Sweep、阈值 Sweep、指标和故障注入均是建议的验证方式；不要在没有证据时声称项目已具备 | 需以当前测试、数据和运行记录为准 |

## 一、经历范围与问题定义（1–10）

1. 你希望承担哪类 AI 应用工程工作？这个 RAG 项目中哪段经历最能证明匹配度？
2. 请用两分钟说明小说转短剧平台为什么需要 RAG：用户问什么、系统从哪里取资料、最终把什么交给生成流程？
3. 选一次真实查询，从 HTTP 请求开始，按执行顺序讲到检索结果进入提示词；每一步分别由哪个模块负责？
4. 你本人实际实现、调试或验证了哪一段？请区分个人贡献、既有代码和你提出但尚未实施的方案。
5. 这套 RAG 处于什么使用或部署阶段？哪些事实有日志、测试或用户反馈支撑，哪些不能仅凭代码推断？
6. 你遇到过最难定位的一次检索或索引问题是什么？如何从表象缩小到根因？
7. 哪个技术选择最影响正确性、延迟、成本或数据一致性？当时的约束和被放弃的替代方案是什么？
8. 如果项目还没有真实线上指标，你会如何诚实地描述成果，并设计一个最小可复现的验证实验？
9. 当前链路最重要的风险是什么？为什么它比“再加一个更大的模型”更值得优先处理？
10. 面试官要求你只用一个案例证明工程能力，你会选哪次索引刷新、检索失败或恢复过程？证据是什么？

## 二、Context 构建与预算（11–20）

11. 当前 retrieve_limit=50 控制了什么？它为什么不是生成上下文的 Token 上限？
12. 900 字符 Chunk、120 字符重叠、最多 50 个命中，分别影响检索、Embedding、提示词体积的哪个环节？
13. 为什么字符数不能可靠代表 Token 数？若生成模型换了 Tokenizer，Context Budget 应在哪一层计算？
14. 当前 1200 字符截断只作用于哪些 fallback 片段？一个事实位于章节后半段时会发生什么？
15. 如何设计 query-aware 长文档定位，避免“精确找到文档，却把不相关的前 1200 字符塞给模型”？
16. 元数据精确命中和事件命中为什么会提前返回？这种低延迟策略在哪些复合问题上可能损失召回？
17. 若本轮召回 50 个片段，如何去重、压缩并保留章节顺序、人物关系和事件因果？
18. 你会怎样定义 Token Budget Layer 的输入和输出？预算不够时，先删哪些资料、保留哪些证据？
19. Lost-in-the-Middle 是什么问题？如何通过上下文排序或分段组织来验证重要证据的位置影响？
20. Source Diversity 配额适合解决什么偏差？硬配额会不会把真正相关的同一来源证据挤掉？

## 三、来源、证据与冲突（21–30）

21. 当前 RagDocument 中的 source_id、source_type、title、content、metadata 分别解决什么问题？
22. 章节原文、章节事件和结构化事件适合回答哪些不同的问题？为什么不能简单地全拼成一份大文档？
23. 当前 Context 展示了来源信息，为什么仍不能说模型输出具备可靠引用？
24. 如果要支持 Citation ID，检索片段、提示词和生成结果分别需要怎样携带来源标识？
25. 如何做引用后处理校验，识别不存在的来源编号、错误章节或与引用内容无关的断言？
26. 章节原文与事件 JSON 对同一剧情给出冲突描述时，系统目前能否自动裁决？你会怎样诚实描述现状？
27. 如果不同来源的权威性不同，怎样设计 source authority，而不是只按向量分数决定？
28. 什么是 Evidence Gate？在 RAG 没找到足够证据时，系统应如何限制模型补写剧情事实？
29. 如何评估引用准确率、引用覆盖率、冲突裁决准确率和 Unsupported Claim Rate？每个指标的分母是什么？
30. 事实检索与创作指导（如美术风格、导演手册）如何分层，避免把建议误当成小说事实？

## 四、召回、排序与评测（31–40）

31. 当前有哪些召回通道？元数据、事件 JSON、向量、词法各自何时执行、何时提前返回？
32. 当前词法路径为什么不能直接称为 BM25？自定义 lexical_score 的匹配信号和限制是什么？
33. RRF 用排名而非原始分数融合，解决了什么量纲问题？它又丢掉了什么分数信息？
34. 当前 RRF 的 60 常数意味着什么？改变它可能怎样改变靠前结果，应该如何验证？
35. RRF 与 Cross-Encoder 的目标和计算成本有什么不同？何时值得增加 Cross-Encoder？
36. 固定 Top-K=50 对简单字段查询和复杂剧情问题分别有什么浪费或风险？
37. 如何建立人工审核的 Golden Set？每条样本至少保存哪些 query、gold source、gold chunk 和 gold answer 信息？
38. 如何做 K Sweep 和向量阈值 Sweep？怎样同时观察 Recall@K、Precision@K、MRR/NDCG、延迟和 Context Token 数？
39. 如果高召回带来很多错误资料，你会怎样定义可接受的 Precision/Recall 取舍，并按查询类型分别评估？
40. 线上反馈说“搜不到刚改的章节”，你怎样判断问题来自数据装载、索引刷新、召回排序还是答案生成？

## 五、Warm-up 调度与增量刷新（41–50）

41. 当前 RAG Warm-up 是在哪里调度的？它与负责长时间章节任务的 Redis Stream Worker 有什么区别？
42. _warmup_tasks 保存了什么？它能避免什么重复工作，又为什么不能协调两个 API 进程？
43. asyncio.create_task 和 asyncio.to_thread 在当前 Warm-up 路径里各自做什么？它们是否意味着任务已经持久化？
44. Warm-up 如何加载项目文档、生成指纹、切块、计算或复用 Embedding，再写入 Chroma？
45. Chunk 内容哈希与 skip_unchanged=True 能减少哪些工作？它不能保证哪些跨进程或跨存储一致性？
46. indexed_ids 和 delete_stale_documents 分别承担什么职责？刷新结束时为什么要删除过期 Chunk？
47. 为什么新文档指纹要等写入和过期清理完成后才记录？异常时指纹不更新能避免什么误判？
48. 在非增量兼容路径中，先清空 scope 再重建有什么风险？中途失败时用户会看到什么？
49. 增量路径直接 upsert 到当前索引时，刷新到一半失败可能留下什么新旧数据状态？
50. Warm-up 目前有哪些可观测日志字段？只看 status=completed 是否足以证明索引内容正确？

## 六、索引一致性、版本与回滚（51–60）

51. “索引写入成功”与“新索引对查询可见”是同一个状态吗？当前实现是否有二阶段切换？
52. 设计 V1/V2 索引版本时，BUILDING、VALIDATING、READY、ACTIVE、FAILED 各状态允许哪些操作？
53. 如何让查询始终只读 active_version，同时让后台 Worker 构建新版本？
54. 验证失败时如何确保旧版本继续服务？切换 active_version 的原子边界在哪里？
55. 用数据库事务切换 active_version 是否足够？向量数据和业务数据库不共享事务时如何处理部分失败？
56. 如何构造故障注入测试：在第 N 个 Chunk、Embedding 超时或删除过期 Chunk 时失败，检查旧版本是否完整？
57. 更新过程中有新一轮源数据提交，正在构建的版本如何检测“构建目标已过期”？
58. 指纹应覆盖哪些字段：正文、事件、元数据、Embedding 模型、切块策略、提示词/解析版本？漏掉后会怎样？
59. Embedding 模型或维度改变时，如何让旧索引继续服务并完成新索引迁移？
60. 原子版本切换、双写、停机重建和增量原地更新各自的复杂度与适用场景是什么？

## 七、Worker、锁与持久化任务（61–70）

61. 为什么不能把当前进程内 Warm-up 说成“Redis Worker 在消费任务”？代码证据在哪里？
62. API 进程重启后，_warmup_tasks、本地 fingerprint cache 和持久化的 Chroma 数据分别会怎样？
63. 如果部署两个 API 实例，同时发现同一项目需要 Warm-up，会发生什么？如何证明是否存在重复 Embedding？
64. Redis 分布式锁的 key、唯一 token、TTL 和安全释放分别解决什么问题？锁过期但原 Worker 仍在运行怎么办？
65. Redis 锁回答“谁能执行”，持久化任务记录回答什么？两者能否相互替代？
66. 为索引任务设计任务表时，你会记录哪些状态、指纹、版本、重试次数、错误和时间字段？
67. Worker 崩溃后，RUNNING 任务如何通过租约、心跳或超时转为可恢复状态？如何避免双重执行？
68. 至少一次投递可能造成重复消息；如何让索引任务具备幂等性？
69. 什么时候需要消息队列，什么时候 API 进程内后台任务足够？以任务时长、重要性、部署拓扑和恢复要求说明。
70. 如果要将 Warm-up 接入项目已有 Worker，任务提交、锁、版本构建、结果落库和前端状态分别放在哪个边界？

## 八、删除、清理与幂等（71–80）

71. 当前删除项目或章节时，业务数据库操作与 Chroma 清理是否联动？请根据服务代码回答，而不是根据设计意图回答。
72. 删除章节后旧向量何时可能被清掉？在下一次索引刷新前，检索路径有什么风险？
73. 项目被删除后，持久化的项目 Chroma 目录和运行时缓存分别可能留下什么数据？
74. 为什么不能只看项目表里已经没有记录，就断言 RAG 数据也已删除？
75. 删除章节需要立即生效时，你会同步删向量，还是写 tombstone 再异步清理？如何避免失败后又检索到旧数据？
76. 删除整个项目时，如何处理业务库、Chroma、缓存、正在运行的 Warm-up 以及重复删除请求？
77. 如何设计删除任务的幂等性、隔离锁和执行后验证？“重复删除已不存在的数据”应视为成功还是异常？
78. 刷新任务与删除任务并发时，怎样避免删除刚完成、旧任务又把资料写回？
79. 项目级物理隔离与 collection 内按 project_id 过滤各有什么删除和权限风险？
80. 设计删除验收时，除了检查数据库，还要检查哪些向量计数、查询结果、缓存和磁盘残留？

## 九、Embedding 失败、可观测性与运行（81–90）

81. Embedding 遇到超时、429、500 或模型不可用时，应该怎样区分可重试错误与不可重试错误？
82. 指数退避、随机抖动、最大重试次数和总任务超时如何协同，避免重试风暴？
83. 如果 Embedding 第 5 批失败，前 4 批已写入当前索引，系统当前会留下什么？如何通过版本化构建降低风险？
84. 如何证明内容未变化时真的跳过了 Embedding？应统计尝试数、成功数还是实际 upsert 数？
85. 为 Warm-up 定义成功率时，分母应包括取消任务、过期任务或无变化任务吗？如何避免指标误导？
86. 你会为检索与索引链路记录哪些关联 ID、项目 ID、fingerprint、索引版本和耗时阶段？
87. 如何区分 queue wait、文档装载、Embedding、Chroma 写入、检索和生成各自的延迟？
88. “用户搜不到刚改内容”需要哪些 Trace/日志字段才能沿数据流定位到具体断点？
89. 多租户项目中，日志如何避免暴露小说正文、用户隐私或供应商凭据，同时保留排障信息？
90. 哪些故障适合自动重试，哪些应降级到旧索引或词法检索，哪些必须停止并提示人工处理？

## 十、系统设计与条件变化（91–100）

91. 请设计一套可靠的章节修改到 RAG 可检索的端到端流程，并标明 API、数据库、任务队列、Worker、Embedding 和向量库边界。
92. 设计前先向面试官确认哪些规模、SLO、更新频率、预算、隐私和可用性约束？为什么这些问题会改变方案？
93. 如果只有一个 API 实例、每天索引更新很少，最小可靠方案是什么？哪些复杂组件可以暂缓？
94. 如果有多个 API/Worker 实例，且一次 Warm-up 要运行数分钟，怎样实现跨实例去重、故障恢复与进度追踪？
95. 如果要求章节修改后 2 秒内可检索，你会选择同步更新、双写、增量索引还是缓存旁路？代价是什么？
96. 如果索引规模扩大 100 倍，最先观察哪几个指标？如何判断瓶颈在 Embedding、Chroma、I/O、锁竞争还是 Context 构建？
97. 如果人工评测显示 Recall 提升但答案准确率下降，你会如何区分召回噪声、排序、Context 预算和生成幻觉？
98. 请提出一套最小上线验收：功能正确性、索引一致性、删除验证、故障恢复、成本/延迟和回滚各如何测试？
99. 做一次优化后，你怎样报告业务收益？如果没有真实用户数据，如何用离线评测和任务耗时实验，不夸大结论？
100. 回顾整个方案，哪些能力是你已实现并验证的，哪些仍是设计建议？下一步你会选择一个什么范围可控、可量化的改动？

## 建议的练习顺序

- **10 分钟项目开场**：第 1–10 题选 2 题，讲清实际职责与项目阶段。
- **20 分钟代码深挖**：第 11–20、41–50、71–80 题各选 2 题，打开代码按数据流解释。
- **15 分钟工程设计**：第 51–70 题选 3 题，重点解释当前实现与目标架构的差距。
- **10 分钟评估复盘**：第 31–40、81–100 题选 2–3 题，使用可复现指标，不虚构业务成果。

## 作答自检

- 我有没有讲清用户问题、输入、输出和我的个人责任？
- 每条“当前已实现”是否有代码、测试、日志或数据证据？
- 是否把进程内任务、Redis Worker、线程池和持久化任务状态混为一谈？
- 是否把 RRF 误称为 BM25 或 Cross-Encoder？
- 是否把召回条数上限误称为 Token Budget？
- 是否把“提出了方案”说成“已经实现/上线/产生业务收益”？
- 指标是否有明确基线、分母、样本量和测试条件？
- 对尚未解决的问题，是否能说清风险、调查步骤和最小验证方案？
