# 面试项目-小说转项目

## 项目 RAG 一句话概括

该项目不是单纯的向量 Top-K，而是一个“是否需要检索判断 → 查询意图解析 → 精确检索 → 结构化事件检索 → 向量与关键词混合检索 → 关键词降级 → 上下文注入”的分层 RAG。

```text
用户问题
  ↓
判断本轮是否需要 RAG
  ↓
解析查询意图与检索工具计划
  ↓
元数据精确检索
  ↓ 未命中
结构化事件检索 + 对应章节正文
  ↓ 未命中
语义向量检索 + 高精度关键词检索
  ↓ 未命中 / 向量不可用
宽松关键词兜底
  ↓
按来源去重、排序、截断
  ↓
注入 Agent 系统提示词
```

## 当前项目的关键实现

- 数据来源：项目基本信息、小说基本信息、章节正文、章节事件、结构化事件、美术风格、导演手册等 Markdown 技能资料。
- 文档结构：统一转换为 `RagDocument(source_id, source_type, title, content, metadata)`。
- Embedding：本地 `bge-small-zh-v1.5`，ONNX Runtime CPU 推理，默认 512 维。
- 向量库：Chroma，按项目持久化与隔离。
- 默认切块：900 字符，重叠 120 字符。
- 默认召回上限：50；最低向量分数：0.35。
- 查询意图：优先调用项目文本模型解析，默认 2 秒超时；失败后使用本地规则。
- 增量索引：稳定 chunk ID + 内容哈希；跳过未变化块，清理过期块。
- 容错：向量不可用时走关键词检索；整个 RAG 准备失败时返回空上下文，不中断聊天。
- 一致性取舍：聊天不等待索引重建，发现资料变化后在 API 进程安排异步刷新，本轮可能继续使用旧索引。
- 普通对话：RAG 结果注入系统提示词，也通过 `get_rag_context` 暴露给 Agent；该工具只读取本轮结果，不会二次检索。
- 阶段生成：除了 RAG，还直接注入创作配置、前序工作区以及配置章节范围内的结构化事件。

## 一、项目理解

1. 请完整描述一次用户提问从 API 到 RAG 上下文注入模型的链路。
		首先用户问题--判断是否需要rag--识别意图决定需要用什么工具--元数据精确查找-未命中-结构化事件检索--未命中--语义向量检索RRF--未命中--关键词兜底--去重，排序，截断--注入agnet提示词
2. 为什么不是所有请求都执行 RAG？哪些问题会跳过检索？
	1. 元数据和结构化事件，比如说，小说作者，出版号，每个章节提取的事件，减少模型的调用，token的消耗，规模足够大，会有去重，排序，截断来处理多余内容
3. 知识来源有哪些？怎样统一成 `RagDocument`？
	1. 项目信息--来自项目配置，导演手册，风格，也就是立项的时候输入的信息
	2. 小说信息--作者，来源，更新状态，标题，最后更新，最新章节，分类
	3. 章节正文--一章一条，章节序号，标题，正文，事件（未分类成metadat）
	4. 事件--事件类型，冲突，结果，角色，场景，组织，以及章节信息
	5. 技能--只读项目中选择的那一套技能，视觉风格和导演手册
4. `source_id`、`source_type`、`content`、`metadata` 分别有什么作用？
	1. ragdocument的源文件，目的表明源，类型，向量内容，metadat，目的是为了检索方便，一开始先关键词检索--再向量检索+关键词--关键词兜底
5. 为什么 RAG 按项目隔离，而不是按用户隔离？
	1. 主要目标物是小说，一个项目意味着这部小说，整体工作场景也围绕着修改这部小说展开
6. RAG 查询失败后，为什么聊天还能继续？
	1. 应为有兜底方案，当rag出现失败，也许是网络，模型等原因失败后，会fallback到关键词检索
7. `get_rag_context` 是动态检索工具，还是本轮结果读取工具？
	1. 
8. 普通对话与阶段创作使用 RAG 的方式有什么不同？
	1. 普通对话的rag走的是阶段检索--默认只读工具--系统提示词--查询词是用户的一句话
	2. 阶段创作，进入阶段检索--一句话生成请求---阶段提示词，不绑定工具
9. 阶段生成为什么还要直接注入章节事件？
	1. 形成阶梯检索rag，章节事件优先向量检索，减少token
10. RAG 内容在哪里、以什么形式注入模型？
	1. 512维向量，从ragdocument的conetent切成向量，注入ChromeDB里
	2. bge-embdeindg-v1.5

## 十、资深面试官的项目追问

### 1. API 进程内 warmup 可靠吗？

不完全可靠。进程重启会丢任务，多 Worker 会重复构建，没有跨进程锁、持久化状态和可靠重试。当前实现适合单机或早期阶段，生产规模扩大后应迁移到可靠任务队列或数据库任务表。

### 2. 每次全量加载资料并计算指纹的问题是什么？

数据库读取、内存占用与 O(N) 哈希成本随章节数量增长。可以把项目资料版本保存在业务库，由变更事件推动索引增量更新；查询只读取版本号，不重新遍历全部资料。

### 3. 当前混合检索最大的不足是什么？

- 没有独立 Reranker。
- 检索分支提前返回，可能漏掉跨通道更优证据。
- 各通道分数缺乏统一标定。
- Top-K 与上下文预算是固定配置。
- 同一来源只保留一个 Chunk 可能丢失分散在文档不同位置的证据。

### 4. 阶段生成同时注入 RAG 和大量章节事件有什么风险？

内容重复、上下文过长、重要信息被截断、模型注意力稀释。可按当前集和章节规划分批检索，使用层级摘要，给不同资料类型分配 Token 预算，并增加引用与覆盖检查。

### 5. 为什么索引过期时仍允许使用旧索引？

这是延迟与一致性的取舍。主请求不等待重建可以保证响应时间，但需要暴露索引版本、陈旧状态和更新时间；对尚未入索引的新资料，可使用当前内存文档的关键词检索补偿。

### 6. 怎样证明你的 RAG 策略有效？

建立真实问题集和事实级标注；分别评估精确查询、事件检索、向量检索、词法兜底；测 Recall@K、MRR/NDCG、事实忠实度、引用准确率、延迟和 Token 成本；再用消融实验比较关闭每个分支后的指标变化。

## 面试时的核心观点

资深面试官看的不是是否会背向量数据库，而是能否解释：

1. 为什么为不同问题选择不同检索策略；
2. 如何通过评测证明策略有效；
3. 失败时如何降级并保证主链路可用；
4. 如何处理索引一致性、租户隔离和 Prompt Injection；
5. 数据规模、并发和部署复杂度扩大后，哪个部分会最先成为瓶颈。
