# 小说转短剧 AI 平台：100 个 Agent 面试题（SolThink版）

> 本版严格聚焦 Agent，采用“问题 → 30秒口述 → 深挖证据 → 边界/优化”的面试教练结构。项目事实来自 `NovelToVideo` 当前仓库；个人贡献不能仅由源码证明，涉及“我负责”的位置必须替换成你的真实经历。

## 使用原则

面试回答固定使用四层：

1. **我解决什么问题**：先讲业务目标，不先报框架名。
2. **我怎么设计**：解释为什么由代码控制、为什么由模型控制、为什么要有状态/工具/Worker。
3. **我怎么证明**：给出源码位置、日志、测试或可复现实验。
4. **哪里还不完美**：主动说边界，再给出下一步设计。

### 一个重要边界

- **源码存在 ≠ 我本人实现。** `chat.py`、`stage_generation.py`、`team.py` 等存在，只能证明项目有这条能力。
- **实现存在 ≠ 已验证所有供应商。** 尤其是原生 `tool_calls` 的端到端兼容，需要真实 provider 响应验证。
- **有恢复代码 ≠ Agent checkpoint 完整。** Worker 任务恢复与 Agent 对话 checkpoint 是两个不同问题。
- **有多 Agent ≠ 动态 Agent。** 当前 CrewAI 团队是业务代码定义角色、顺序和上下游 context，模型不负责动态改拓扑。

## 项目 Agent 架构速记

```text
用户请求
   ↓
chat.py：鉴权 / 会话锁 / 状态加载 / 请求分流
   ├── 普通对话 → DeepAgentsRuntime → HarnessAgent
   │                  ↓
   │             Tool 执行 / 事件流 / 最终回答
   │
   └── 阶段生成 → stage_generation.py
                      ↓
               阶段前置闸门 / EP 计划
                      ↓
               CrewAIStageRuntime
                      ↓
        分析 → 设计 → 编写 → 审校（顺序）
                      ↓
            quality.py 质量门禁
             ├── 通过 → 工作区 + DB
             └── 失败 → 自修复 / 回滚 / 人工确认

长任务：
业务任务 → TaskJob/TaskItem(DB) → Redis Stream → TaskWorker
                                  ↓
                         heartbeat / retry / scavenger
```

## 已核对的关键源码事实

| 主题 | 当前项目事实 | 关键代码 |
|---|---|---|
| 主 Agent | 通过 `HarnessAgent` 抽象具体 runtime；普通聊天默认走 DeepAgents | `core/harness/runtime/agent.py`, `deepagents.py` |
| 阶段 Agent | 默认 CrewAI 顺序团队 | `services/screenwriting/team.py`, `core/harness/runtime/crewai.py` |
| 团队成员 | `tools=[]`、`allow_delegation=False`、`max_iter=1`、`max_retry_limit=0` | `crewai.py` |
| 工作流 | skeleton→strategy→script 有业务代码前置闸门 | `stage_generation.py` |
| 会话 | DB 持久化 + 进程内短期状态/锁 | `state.py` |
| 工具 | 当前编剧工具集是只读：配置、工作区、小说事件 | `agent_tools.py` |
| Provider | OpenAI-compatible 文本 Provider；流式网关采用块间空闲超时 | `agent_gateway.py`, `provider_runtime.py` |
| 原生 tool_calls | 适配层这里主要把响应转成文本 AIMessage，是否端到端保留 tool_calls 需要联调证明 | `chat_model.py` |
| Worker | Redis Streams + DB 状态、并发、超时、heartbeat、retry、scavenger | `tasks/engine.py`, `worker.py`, `scavenger.py`, `tasks.py` |
| 任务默认值 | batch=4、concurrency=4、timeout=3600s、heartbeat=30s、retries=3、backoff=30s、stale=600s | `core/tasks/constants.py` |

## 十一、SolThink高压追问：最容易被问穿的 12 个点

### 1）“你说用了 Agent，为什么不直接写死流程？”
因为内容生成需要语言理解，但状态转移、权限、任务恢复和持久化必须确定性。当前项目就是“代码定流程、模型定内容”。

### 2）“你说是多 Agent，模型真的自己决定 Agent 拓扑吗？”
不是。当前 CrewAI 团队成员、顺序和 context 方式都由 `team.py` + `CrewAIStageRuntime` 固定定义；它不是动态规划 Agent。

### 3）“thread_id 有了，是不是就有 checkpoint？”
不是。当前 DeepAgents 运行时传入 thread_id，但没有在构造 Agent 时显式配置持久化 checkpointer/store；真正的业务事实源仍是 `ScreenwritingSession`。

### 4）“Worker 的恢复是不是 Agent checkpoint？”
不是。Worker 恢复的是 TaskItem/Redis Stream 生命周期；Agent checkpoint 是模型运行过程中的中间状态，两者生命周期和一致性语义不同。

### 5）“为什么工具一定不能相信模型参数里的 user_id？”
因为模型输出是不可信输入。真正的用户身份应该来自认证上下文，资源归属必须在服务端再次校验。

### 6）“如果 ACK 丢了，你会不会重复执行？”
Redis 层面消息可能再次可见，但数据库条件抢占会判断 TaskItem 是否仍可运行；终态 item 不再满足 runnable 条件，因此重复消息不会再次成功执行。

### 7）“heartbeat 还在，是不是任务就健康？”
不一定。heartbeat 只证明 Worker 仍活跃，不能证明 provider 请求在有效推进。生产上需要 request deadline、provider latency 和 execution progress。

### 8）“现在有没有 fencing token？”
从当前已核对的任务代码看，没有看到完整的 fencing token 机制。可以通过 execution version/token + 条件写入补强旧 Worker 误写问题。

### 9）“多 Agent 为什么不并行？”
因为当前角色之间存在显式上下游依赖，且团队目标是稳定的阶段流水线。并行应该作为后续优化，而不是为了‘看起来高级’强行增加复杂度。

### 10）“模型输出错了，为什么不能只重试一次？”
因为要区分模型调用失败、格式失败、业务质量失败和确定性错误。不同错误的 retry policy 不同，而且必须受总 deadline 和 max_attempts 约束。

### 11）“你如何证明 tool calling 真跑通？”
不用页面演示证明。要用 fake model 和真实 provider 两套测试：前者证明执行闭环，后者证明供应商原生响应能被适配层正确转换成 runtime 可识别的 tool call。

### 12）“你的 Agent 项目现在最大的短板是什么？”
不是缺更多框架，而是生产级证据还可以继续补：供应商 tool_calls 兼容性、跨实例一致性、版本可追溯、fencing、统一 trace，以及真实业务质量与工时收益基线。

## 十三、两周 Agent 改进计划

### 第 1–2 天：证据收口
固定当前主链路、列出所有 runtime、工具和任务状态；为每个“我做过”的简历点补源码、测试或 commit 证据。

### 第 3–4 天：tool calling 兼容性
建立 fake model、OpenAI-compatible 正常响应、native tool_calls、空 content、异常响应五类测试；明确哪些 provider 已验证，哪些仅支持协议层。

### 第 5–6 天：跨实例一致性
双实例同时打同一会话，验证进程内锁边界；根据结果决定是否补 Redis/DB 分布式协调。

### 第 7–8 天：Agent 恢复
对阶段生成做进程 kill/restart；验证已完成 EP 是否重复、pending repair 是否恢复、工作区是否可恢复。

### 第 9–10 天：Worker 幂等与 fencing
注入 ACK 丢失、旧 Worker 恢复、重复消息，验证 DB 条件抢占、retry 和最终结果一致性。

### 第 11–12 天：角色级质量门禁
给一个中间角色设计结构化输出 schema，故意制造坏输出，验证只重试失败角色而不是重跑完整团队。

### 第 13–14 天：业务基线
建立单 Agent vs 顺序团队 A/B，固定数据集与模型，记录质量、成本、延迟和人工修订时间，输出是否值得上线的结论。

## 十五、最终口述模板：90 秒 Agent 项目回答

“我这个项目不是简单把大模型接进来，而是把模型放进了一套确定性的应用执行框架里。普通编剧对话通过 Harness 统一 Agent 接口，具体走 DeepAgents；阶段创作由业务代码做阶段识别和前置闸门，再交给 CrewAI 顺序团队。团队内部按分析、设计、编写、审校协作，代码控制顺序和状态，模型负责内容生成。工具层目前是只读工具，避免模型直接修改配置；会话状态和工作区写入数据库，进程内缓存和锁负责运行态。长任务则走独立的 Redis Stream + DB TaskItem + Worker + heartbeat + retry + scavenger 机制。对阶段输出还有质量规则、自修复、单集回滚和人工确认。我的面试重点会放在我真正负责的那一部分，并用源码、测试和故障证据证明，不把框架名称当能力证明。”
