# 小说转短剧 AI 平台：100 个 Agent 面试题

> 面试视角：高级 AI 应用工程师，针对项目经历做递进式追问。题目重点考察实际负责范围、技术判断、验证方式、故障复盘和经验迁移；不会把框架名称或功能清单当作能力证明。

## 面试使用方式

这是分层题库。按面试时间和候选人经历选择问题；先让候选人完整讲一个自己最熟悉的项目案例，再沿着案例往下追问。

### 通用追问阶梯

每个技术回答都可沿以下顺序深挖，已经讲清的环节不必重复问：

- **个人负责：** 你具体做了什么？哪部分是你本人负责的？
- **问题与约束：** 当时的问题、约束和成功标准是什么？
- **技术判断：** 为什么选这个做法？考虑过哪些替代方案？
- **验证证据：** 你如何验证？请给出代码位置、运行轨迹、测试或数据口径。
- **失败复盘：** 出过什么问题？哪些仍未解决？你从中改了什么判断？
- **条件变化：** 如果模型、数据量、并发、延迟目标或成本约束改变，方案要怎么调整？

回答时区分“代码中存在”“自己跑过验证”“准备采用的改进方案”。没有真实用户数据、上线记录或指标时，明确说明证据边界。

## 一、方向、经历与个人负责范围（1–10）

1. 你目前希望做哪类 AI 应用工程工作？Agent 项目里哪段经历最能代表你的能力？
2. 请用两分钟介绍小说转短剧平台解决的业务问题、主要用户和从输入到产出的流程。
3. 这个项目目前处于什么使用和部署阶段？你如何确认，而不是根据代码结构推断？
4. 项目里你亲自完成了哪些工作？请用代码、调试记录、实验或交付物逐项说明。
5. 哪些模块由你独立设计和实现，哪些是既有代码、他人工作或你只参与调试的部分？
6. 选一项你负责的 Agent 能力，从需求到交付完整讲一遍，并说明中间有哪些人或系统参与。
7. 你在项目里做过哪一个影响最大的技术决定？当时的约束、备选方案和结果分别是什么？
8. 讲一次你通过断点、日志或数据库状态定位问题的经历：最初判断是什么，证据如何改变了判断？
9. 项目里哪项能力目前最不完善？你怎样向面试官或使用者准确说明它的边界？
10. 如果只能展示一个项目成果来证明你能交付 AI 应用，你会展示什么？如何让别人复现并检查？

## 二、业务问题与 Agent 方案选择（11–20）

11. 章节事件提取或剧本生成分别替用户完成什么工作？你会用什么证据判断它确实高频、重复或耗时？
12. 为什么这个任务需要大模型？哪些部分用普通 Python 规则或数据库查询会更稳定？
13. 如何把“小说变成短剧”拆成可验证的子任务？每个子任务的输入、输出和验收条件是什么？
14. 本项目哪部分适合 Agent，哪部分更适合固定流程？请指出代码中控制分支的实际位置。
15. 小说事件提取通过异步 Worker 执行时，它与编剧 Agent 的对话/创作运行时分别解决什么问题？
16. 阶段创作被描述为多 Agent 时，当前实现里哪些行为是模型决定的，哪些由固定顺序和业务代码决定？
17. 选一个看似适合 Agent 的步骤，说明使用 Agent 相比固定工作流增加了什么收益、成本和故障面。
18. 上线前你会与创作者确认哪些约束：原著忠实度、人物一致性、单集时长、审核点还是成本上限？为什么？
19. 如果没有真实用户访谈或耗时基线，你会怎样验证问题值得自动化？怎样避免把自己的假设当业务事实？
20. 请画出一个章节从导入、提取事件、检索到剧本产出的数据流，并指出每个模型调用的目的。

## 三、工具调用与最小执行循环（21–30）

21. 从模型提出工具调用开始，到服务端执行并把结果交回模型，完整闭环包含哪些步骤？
22. 模型生成了工具名称和 JSON 参数，谁负责真正执行函数？为什么不能让模型输出直接成为可信的执行命令？
23. 如何给读取项目配置、工作区和小说事件的工具设计清晰描述与参数 Schema，减少误选和歧义？
24. 工具调用参数如何做类型、必填项、枚举、长度和额外字段校验？校验失败后你会如何反馈？
25. 项目 ID、用户 ID 和访问权限由谁提供？为什么不应只依赖模型生成的参数？
26. 代码中工具已经绑定到 Agent，如何进一步证明模型确实发出调用、运行时执行了工具、结果又回到了模型？
27. 如果模型供应商返回原生 tool_calls，而适配层只把 content 转成普通 AIMessage，可能发生什么？你会如何沿代码和日志验证？
28. 请脱离 LangChain、DeepAgents 和 CrewAI，现场写一个最小 Python Agent 循环：模型调用、工具分派、结果回填和结束判断都要有。
29. 为这个循环设置最大轮数、总超时、未知工具拒绝和参数错误处理时，你会把限制放在哪一层？
30. 你会怎样用 fake model 测试直接回答、一次工具调用、连续调用、工具异常和超限？每个测试要断言什么？

## 四、工作流与阶段编排（31–40）

31. 请按代码追踪一次普通编剧对话：HTTP 入口、鉴权、加载状态、RAG、Agent、保存和流式返回分别在哪里？
32. 请追踪一次阶段生成：阶段识别、前置条件、RAG 上下文、团队执行、质量检查和产物保存依次如何发生？
33. 普通聊天和阶段创作采用不同 Agent runtime 时，共用哪些输入输出契约？差异在哪里？
34. 阶段缺少前置产物时，当前代码如何处理？这种固定依赖带来什么好处，又会限制什么场景？
35. 哪些流程分支必须由代码确定，哪些内容可以交给模型生成？如果把分支也交给模型决定，风险是什么？
36. 剧本按集生成时某一集失败，当前流程如何保留已有结果或要求用户介入？你如何验证失败边界？
37. RAG 准备异常时，当前聊天链路是失败、降级还是继续？这个选择可能带来什么剧情事实风险？
38. 阶段 Agent 之间如何交接上下文和产物？怎样避免后一阶段把前一阶段的臆测当成原文事实？
39. 如果已排队任务遇到 prompt 或工作流升级，系统怎样保证执行版本可追溯？当前记录是否足够？
40. 你会怎样把工作流画成状态图，并覆盖成功、失败、修复、用户确认、取消和重试这些转移？

## 五、状态、会话与记忆（41–50）

41. Agent 的本轮状态、对话历史、创作工作区、RAG 索引和异步任务状态各自应该保存什么？
42. 本项目会话状态哪些写入数据库，哪些留在进程内缓存？请用代码或重启前后实验作证。
43. project/user 会话隔离键、conversation ID、Agent thread_id 和异步任务 ID 分别是什么？它们是否可以互换？
44. 传入 thread_id 就代表 Agent 有持久化 checkpoint 吗？你会检查哪些 runtime 配置和存储实现来确认？
45. 当前会话锁位于进程内时，两个后端实例同时收到同一会话请求会怎样？如何复现并验证？
46. RAG 检索结果、模型对话历史和 Agent 长期记忆有什么区别？本项目实际实现了哪几种？
47. 小说新增或修改后，如何判断本轮上下文和向量索引是否使用了最新内容？
48. 如果工作区摘要和原文事件冲突，Agent 应以什么作为事实来源？如何展示冲突并让人修正？
49. 删除章节或项目后，数据库、Chroma、缓存和历史快照如何保持一致？当前清理链路覆盖到哪里？
50. 如果需要恢复一个中断的阶段生成，你会持久化哪些 checkpoint，并怎样处理 checkpoint schema 升级？

## 六、多 Agent 协作与角色边界（51–60）

51. 本项目一个阶段团队包含哪些角色？请讲清角色顺序、上下游输入和最终产物。
52. 当前团队使用顺序执行时，为什么不用并行？哪些任务依赖前一角色结果，哪些理论上可以并行？
53. 角色目标和提示词怎样拆分，才能减少输出重复并让交接内容可检查？
54. 如何约束每个角色输出结构？如果某角色只返回自然语言但下游需要结构化字段，如何发现和修复？
55. 多个 Agent 对人物设定或事件因果意见不同时，谁裁决？需要引用原文证据还是由审校 Agent 投票？
56. 在角色之间传递完整历史、结构化产物和摘要，各有什么代价？你会如何选择并测量质量损失？
57. 当前 CrewAI 成员不带工具且不委派子 Agent，这说明团队目前能做什么、不能做什么？
58. 如何用同一批小说样本比较单 Agent 与顺序团队？请说明质量评审盲法、成本统计和失败样本处理。
59. 如果中间角色输出质量差但最终角色仍生成了内容，如何阻止错误层层传播并保留可复用结果？
60. 如果要将固定团队改成动态规划或并行协作，你会先补哪些状态、权限、预算和停止规则？为什么？

## 七、失败处理、重试与恢复（61–70）

61. 模型请求超时后，服务端能否断定供应商没有完成任务？如果结果已生成但响应丢失，重试会造成什么？
62. 哪些错误适合自动重试，哪些应立即失败或转人工？请用限流、网络中断、无效 JSON、权限拒绝举例。
63. 如何设置重试次数、退避、随机抖动和总截止时间，避免多个任务同时重试压垮模型服务？
64. Agent 运行到一半进程退出后，重启时如何判断从头运行还是从某个安全节点继续？
65. Redis Stream 消息已被 Worker 处理，但 ACK 丢失时会发生什么？怎样避免重复生成和重复写入？
66. Worker 心跳能够证明什么？如果心跳还在更新，但模型请求长期卡住，系统怎样检测和处理？
67. OrphanScavenger 恢复超时任务时，如何阻止原 Worker 恢复后继续写入？需要 fencing token 或条件更新吗？
68. 数据库提交、Redis ACK 和模型外部副作用不能组成一个原子事务时，你如何保证最终状态可恢复？
69. 达到重试上限后，用户、任务状态、日志和人工支持人员分别应该看到什么信息？
70. 用户取消一次流式创作时，如何处理模型取消、已发送文本、持久化、半成品工作区和最终状态？

## 八、权限、安全与人工审核（71–80）

71. 请沿一个编剧 API 请求说明 JWT 校验和项目归属校验在哪里发生；仅看前端路由为什么不够？
72. 任务进入 Worker 后，用户和项目身份如何随消息传递？后台处理是否需要重新检查资源归属或状态？
73. 只读查询工具和会修改工作区、发布内容的工具，应如何区分权限、授权和审计要求？
74. 如果小说原文包含提示注入，如何确保它仍被当成待分析数据，而不是系统指令？
75. 模型要求工具访问另一个项目或其他用户的章节时，工具执行层如何拒绝并记录？
76. 为了定位问题，哪些 prompt、原文、工具参数和返回值可以记录？哪些要脱敏、摘要或限制访问？
77. 哪些产物需要人工批准后才能进入下一阶段或对外发布？审核状态、审核意见和重生成如何留痕？
78. 规则检查、LLM 自评和人工审核各自负责什么？如何处理三者意见不一致？
79. 用户要求删除项目数据时，怎样确认对话、模型日志、索引、缓存和第三方存储都按保留策略处理？
80. 如果将来接入高风险工具，怎样设计权限确认、操作预览、二次审批、幂等键和撤销/补偿？

## 九、评估与业务收益（81–90）

81. 你会怎样建立本项目的 Agent 评测集？如何覆盖常见任务、长篇上下文、人物混淆、冲突、拒答和失败恢复？
82. 事件提取、骨架、改编策略和剧本生成的“成功”定义分别是什么？为什么不能只用一个总分？
83. 如何定义工具选择准确率、参数有效率、工具执行成功率和端到端完成率？每项指标的分子、分母是什么？
84. 事件字段的 Precision、Recall、F1 和整条记录准确率怎样计算？部分正确的事件该如何评分？
85. 如何评估剧本对原著事实的忠实度、人物一致性、因果链和可拍摄性？哪些判断要由领域人员完成？
86. 如何维护模型漂移、坏 JSON、工具失败、检索过期和长上下文失效的回归样例？数据如何避免泄漏到 prompt 调优集？
87. 更换模型或 prompt 后，如何做对照实验和回归？报告里必须写明哪些样本规模、测试条件和统计口径？
88. 怎样计算“每个成功交付章节/剧本”的总成本，而非只报一次模型调用价格？
89. 怎样测量节省工时？如何纳入人工审核、修订、失败重跑和系统维护时间，并与同口径人工基线比较？
90. 如果目前没有真实用户、样本或节省工时数据，你会如何诚实陈述现状，并设计下一步验证？

## 十、运行、性能与约束变化（91–100）

91. 一次 Agent 请求的 trace 要关联哪些 request、user、project、conversation、workflow run、tool call 和 provider request 标识？
92. 如何记录足以复盘工具选择和状态变化的信息，同时避免把小说全文、用户隐私或 API Key 写进普通日志？
93. 如何分别测量排队时间、RAG 准备时间、模型首 token 时间、工具耗时和端到端耗时？平均值之外还要看什么？
94. 本项目使用 NDJSON 流式返回时，客户端断开、网络分块和任务完成状态之间分别是什么关系？如何避免前端显示完成而数据库仍失败？
95. 当前任务指标或日志能回答哪些运维问题？哪些生产监控、告警和供应商可用性指标仍需要补充？
96. 模型限流、延迟升高或供应商不可用时，如何设置并发限制、排队、熔断、降级和用户反馈？
97. 如果便宜模型速度快但事件准确率较低，你会如何用离线评测结果决定模型路由和人工复核阈值？
98. 假设同时有 100 个用户各提交 100 章清洗与创作任务，你会如何估算队列、Worker 并发、模型限额、数据库压力和存储增长？
99. 上线 prompt、模型或 Agent 流程的新版本时，你会如何灰度、观察指标、暂停和回滚？哪些任务要固定旧版本继续执行？
100. 请设计这套 Agent 的长期运行方案：从需求基线、工具权限、工作流状态、审核、恢复、观测、质量评估到工时收益，指出当前代码证据、未验证项和下一步实验。

## 面试官的判断维度

| 维度 | 强证据 | 需要继续追问 |
|---|---|---|
| 个人负责范围 | 能指出本人完成的代码、决策、调试或实验 | 只罗列框架与功能，分不清个人和团队贡献 |
| 技术判断 | 能解释约束、备选方案及取舍 | 只说“行业都这么做”或“框架默认如此” |
| 验证能力 | 能复现并提供日志、测试、样本和指标口径 | 只凭页面演示或主观感觉判断成功 |
| 故障责任 | 能讲清失败、影响、处理及残余风险 | 把重试、心跳或异常捕获说成绝对可靠 |
| 经验迁移 | 条件变化时能指出方案何处需要重做 | 机械复述当前实现，不能说明扩展边界 |

## 项目事实核对清单

以下是出题时从仓库代码与说明文档检查到的事实，面试回答仍应根据当前分支重新核验：

- 普通编剧对话通过 DeepAgents runtime；阶段生成使用 CrewAI 的顺序执行。
- 阶段流程由业务代码做请求识别和前置阶段处理；CrewAI 成员配置为无工具、不委派。
- 编剧状态有数据库持久化与进程内缓存/会话锁；DeepAgents 调用传入 thread_id，但构造 Agent 时没有显式配置持久化 checkpointer/store。
- ProviderGatewayChatModel 的字典响应路径提取文本并把原响应放入 metadata；stream 路径主要产出文本 chunk。原生 tool_calls 是否端到端执行，需要联调和测试确认。
- 小说事件提取 Worker 使用 Redis Streams 和数据库任务状态；不要把 Worker 的消息恢复机制说成 Agent 对话 checkpoint。
- 项目代码事实参考：services/screenwriting/chat.py、stage_generation.py、state.py、agent_tools.py；core/harness/runtime/、core/harness/tools/chat_model.py；core/tasks/worker.py、scavenger.py。

## 复习顺序建议

- 第一轮：2、4、6、14、15、21、28、31、42、61、71、84、89、100。
- 第二轮：每个回答都使用“我负责什么 → 为什么这样做 → 如何验证 → 出过什么问题 → 条件变化怎么办”的结构。
- 准备代码演示时，优先独立写第 28 题的最小执行循环，再做第 30 题的 fake model 测试。
- 任何指标都同时说明基线、分母、样本量、测试条件、绝对变化或相对变化；没有数据就标注为待验证。
